#### 步驟 3 的更正：要先「最小化」，不是直接 F5

原本寫的是「按 F5 重新整理 → 仍是 6 位」。實測直接 F5 之後**名單整個不見**（連晶片都沒有）。
查下去發現不是 widget 的問題，是 demo 外殼 `App.vue` 的 `toggleChat` 設計：

- 只有**最小化**（`handleMinimize`）會寫 `traitty_widget_has_active_session` 旗標；
- **關閉**（`handleClose`）會清掉它；
- 下次點啟動器時，沒有旗標就視為「全新開始」，主動清掉
  `traitty_session_active_ids` / `traitty_selected_candidates` / `traitty_batch_reports` 等五個 key。

直接 F5 時 widget 是開著的（沒最小化過），所以旗標從來沒被寫入，重開就被當成新的一輪。
sessionStorage 在重新整理後其實還在（實測讀得到 `[58,59,65,81,82,84]`），是被外殼清掉的。

**照設計的路徑重測——最小化 → 重新整理 → 重開——通過**：晶片回到「選定 6 位人選」，

步驟一致（最小化 → 跳轉 → 返回 → 重開）。

### E-1　自由提問的一千字上限形同虛設

### E-2　`metadata['candidates']` 的歷史資料可能已被截短

- **背景**：`chat.py:449` 把 `candidates_info` 寫進 session metadata，而修好前的 `candidates_info` 是拿分頁清單過濾出來的。切換歷史對話會從這個 metadata 還原名單——所以**修好之後新產生的資料是對的，但修好之前寫進去的可能已經少了人**。
- **查證狀況**：本機 DB 有 232 個 session 帶 metadata、其中 113 個記了 candidates，人數分布 `{1: 60, 2: 49, 3: 2, 4: 1, 11: 1}`，全部 ≤ 11 人。**無法從這裡分辨「本來就只選這幾位」與「被截短過」**——截短不是「砍到 20 位」，而是「與第一頁取交集」，結果可以是任何數字。
- **要做的**：在 UAT／PRD 上比對幾個多人 session 的 metadata 與使用者記憶中的選擇。若確認有被截短的舊資料，需決定是否回填（回填的依據只有 `chat_messages` 裡的內容，不一定夠）。

### E-3　`chat.py` 的守門是單向的

- **現況**：`missing = [c for c in candidates_info if c not in trait_reports]`——只擋「`candidates_info` 有而 `trait_reports` 沒有」。反過來（`trait_reports` 有而 `candidates_info` 沒有、或 `candidates_info` 短於 `candidate_ids`）永遠不會被擋。

### 2026-09-07 續：判定寫出來了，只記錄不判定；並用隨機劇本造樣本

真實流量既然沒有點名式提問，就用劇本造。做了三件事：

**1. `api_v2/services/focus_detect.py`——判定「使用者這輪在問名單上的誰」**

只寫進稽核的 `focus` 欄位（`{names, source, conflict}`），**不參與 `missing_respondents`
的計算、不影響任何攔截**。理由是代價方向：目前 missing 只用於觀察，判太寬只是稽核多
一筆噪音，判太窄會讓真漏人被靜默吸收——而漏人正是整個修正計畫的起點。

判定順序：**排除語 → 點名 → 從歷史繼承（要數量相容）→ 不縮小**。

- **排除語保守處理**：「除了 X 之外」的正確語義是 `名單 - {X}`，而點名偵測會縮成 `{X}`，
  正好相反。反向運算樣本太少、寫錯的代價又與 E-12 同型，所以偵測到就不縮小。
- **無狀態繼承**：不靠跨請求狀態，而是把同一支偵測跑在歷史的使用者訊息上。因此離線可以
  拿舊 log 完整重放；而且名單一變動，前一輪點名的人若已不在名單就自然比不中——
  「名單變動就重設焦點」不必另外寫規則。
- **數量相容**：聚焦一位之後問「他在壓力下如何」該繼承，問「他們兩個誰比較適合」不該——
  兩者都沒有姓名，差別只在指涉的數量。不相容時退回全名單並記 `conflict`。
- **姓名比對比生產版嚴格**（`strict_forms`）：砍掉兩字截斷形。掃回答時偏寬是對的
  （判成沒寫到的代價大），掃提問時代價方向相反——誤中就縮到錯的人身上。

驗收：`scripts/verify_focus_detect.py`，27 條全綠，含「沒有被接進判定」三條
（`completeness_check` 不得引用它、`focus` 只出現在稽核欄位、只在自由提問算）。

**2. `uat_scenarios.py` 新增 S9——隨機多輪對話**

11 種問法樣板（點名／換人／不點名追問／比較／排除／泛稱／整批），隨機名單 3–5 位，
每串固定插入一次「中途加人」，`--seed` 可重現。第 1 輪只抽開場式問法（接續式問法在
沒有前文時測不到東西），每串保證抽得到一次 `followup`（那是繼承路徑唯一的樣本來源）。

刻意不用 LLM 生成提問：樣板可重現，而且形狀分佈可控——隨機生成的句子九成會落在
「泛稱」，正好是已經有 92 筆的那一類。

| 判定 | 筆數 |
|---|---|

**要記住的方法論**：「使用者這輪在問誰」是**提問的屬性，不是回答的屬性**。同一個樣板
在 `101-t1` 只寫了被點名的那位、在 `411-t2` 寫了全部三位——模型自己就不穩定。所以人工
標註要標**提問**，不能拿回答當標準答案。

**兩個實務限制**：

- `/chat/` 有 `30 per hour` 的限流（`chat.py` 的 `@limiter.limit`），第二輪跑到第 26 輪
  就開始拿 429。要收更多樣本得分次跑。
- 4 筆 `excluded` 裡，模型有 3 筆**沒有遵守排除語**（回答仍寫到被排除的那位）。這反而
  證明「保守不縮小」是對的：若照排除語去算 `名單 - {X}` 而模型仍寫了 X，就會生出新的
  誤判。

**以下為當初的記錄，保留備查。**

**2026-09-07 由 S8 劇本發現。嚴重度：高（直接改變使用者拿到的答案）。**

Unit 2 的覆蓋率檢查假設「每一則自由提問都是在問整個名單」。使用者一旦點名——

那四位接在後面。實測：5887 字的回答裡約 79% 是使用者沒問的內容，而且它們有 `###` 標題，

**建議做法**：提問裡出現名單上的姓名時，把期待覆蓋的集合縮成「被點到的那幾位」。
比對用的 `name_forms` 已經存在（`completeness_check.py`），現在只用在回答上，

2. 不點名的追問（S8 第 3 輪的「他」）靠的是歷史，不能只看這一輪的提問字面——
   S8 第 3 輪沒有觸發補生成，但那是模型自己寫全了，不是檢查判對了。

**要決定的**：這是產品行為（使用者問一位，要不要給他五位），建議連同 B 類一起讓客戶

**三個各自獨立的根因**：

**1. payload 從頭到尾沒有一句話說有幾個人。** `[本輪判讀對象]` 這個名單宣告原本只有自由
提問才加；題庫題的 `## 【輸入數據】` 下一行直接就是 `### [受測者 | … | RESP_01]`，11 個
標頭散在 2500 多行特質資料裡。指令第九節其實寫了「請逐一說明每個人」，但沒有名單可對，

會議團隊範例只有 **2 個人**，這個取捨從來沒有在 11 人的規模下被驗證過。

**2. 覆蓋率檢查被內文 bullet 騙掉。** 題庫題原本拿「整行」去比對，而 `_MARKED_HEADING_RE`
把任何以 `- ` 開頭的行都當成標題——這篇回答整篇是 `- **標籤**：一整段內文` 的體例，於是
第 1 節的第一條 bullet（列了 8 個名字的那條）**一行就讓 8 個人通過**。重放那一筆：
**11 個人裡 0 個是靠真正的段落標題命中的，全部靠內文。** 補生成因此只拿到 2 個人的
reason，補得完全正確——錯的是 reason。

### E-14　改寫會吃掉段尾的空行，把下一個 bullet 黏進前一段內文

**現象**（2026-09-08 req `399ad86d`）：使用者看到的是

```
- **李 依帆**：她對公平原則有內在堅持…不被既有框架綁住。- **陳 曉玲**：她待人誠…
```

Markdown 裡行中的 `- ` 不會起新項目，所以陳曉玲那一段在畫面上是黏在李依帆的段落裡的。

**根因（2026-09-08 更正）**：第一版寫成「改寫吃掉**段尾**的空行」，那是錯的。段尾早就有
保護——`_clear()` 從 f1ea065d 起就會把 `segment[len(segment.rstrip()):]` 接回去，而稽核的
`after` 欄記的是改寫器的原始回覆、在補回分隔符**之前**，所以看起來像掉了、其實沒有。

真正的接縫在**段首**。`399ad86d` 的 segment 4 原文是 `\n- **陳 曉玲**：…`，改寫回來是
`- **陳 曉玲**：…`——**開頭那個換行沒有被保護**。而前一段的尾端本來就沒有換行：李依帆
那個 bullet 超過 400 字，`Segmenter._take()` 從最後一個句尾切（`。`），切點在行中間。
兩邊都沒有換行，於是黏成一行。

**只補尾端擋不住這個**：能不能黏取決於**接縫兩側**，而長段落被切在句尾時前一段本來就
沒有尾端換行。這一條要寫下來，因為 f1ea065d 修過一次、看起來已經處理完了。

**規模**：掃過全語料所有回答，這種黏住只出現 **1 次**——要改寫剛好落在 bullet 之前才會
發生。罕見，但使用者看得見。

**已修（2026-09-08）**：`_clear()` 同時保留 `lead` 與 `separator`，回傳
`lead + segment.strip() + separator`。`verify_segment_gate.py` 新增 `[13b]`，用一個
「長 bullet 被切在句尾、下一段以換行開頭」的樣本釘住，並確認 `[13]`（段尾）沒有退步。

### E-15　`observe()` 以 segment 為界切行，線上判定與離線重放會不一致

**現象**：同一筆 `399ad86d`，線上判 `missing_respondents: []`，用同一支程式離線重放卻判
「缺陳曉玲」。

**根因**：`CompletenessChecker.observe()` 對每個 segment 各自 `split('\n')`，所以
**segment 邊界等於行邊界**。串流時陳曉玲那個 bullet 自成一段，於是被當成一個標題；
而最終文字裡它是黏著的（E-14），讀者看不到那個標題。

**為什麼要修**：不只是這一筆判錯。**線上比讀者看到的寬鬆，而 0905–0908 的所有回歸量測都是
離線重放**——兩者不一致，那些量測就不是線上行為的代理。稽核記錄可以離線重放，是這整套
判定能被檢驗的前提。

**已修（2026-09-08）**：`observe()` 把未完的行留在 `_pending`，等下一段接上；`finalize()`
先 `_flush()` 再判定。串流的切點是閘門決定的（超過 400 字就從最後一個句尾切），跟 Markdown
的行毫無關係，不該影響判定。

`verify_completeness_check.py` 新增 `[8b]` 四條：分段餵與一次餵判定必須一致、黏在行中的
`- ` 不算新標題、正常換行的兩段仍各自算數、`finalize()` 會收掉沒有換行收尾的最後一行。

### E-16　純追問會讓模型把前一輪的回答整篇重寫一遍

**現象**（2026-09-08 18:12→18:13，同一個 session 的連續兩輪）：

| | `b07f2fdb` | `c4f3f3b3` |
|---|---|---|
| 提問 | 誰最合適當行銷負責 | **還有其他建議嗎** |
| 字數 | 1335 | 1838 |

`c4f3f3b3` 的第一行就是 `b07f2fdb` 的標題「### 以「行銷負責人」此一職位需求而言，最合適的
人選是**謝淑玲**。」。逐字比對：**本輪 1838 字裡有 1209 字（72%）與上一輪相同**，真正新增的
「### 其他建議」從第 1307 字才開始，只佔 29%。使用者問「還有其他建議嗎」，得到的是一整份重讀。

不是複製貼上——標點從半形變全形（「整合資源,推動」→「整合資源，推動」），是**模型重新生成
了一次**。所以這不是串接錯誤（E-14 那一類），payload、閘門、補生成全都正常，補生成 0 次。

**規模**：把全語料每一個「有前一輪可比」的追問輪都算一次重複率（去標點後做最長共同子序列）：

| 日期 | req | 重複率 | 前輪字 / 本輪字 | 提問 |
|---|---|---|---|---|
| 09-07 | `e4147c25` | **80%** | 5887 / 6042 | 換 蔡雨築 是否同樣的結論說明。 |
| 09-08 | `c4f3f3b3` | **72%** | 1335 / 1838 | 還有其他建議嗎 |
| 09-05 | `896b2143` | **68%** | 2220 / 2285 | 再一次排序。 |
| 09-07 | `ffe409c4` | **52%** | 1234 / 1224 | 除了 蔡雨築 之外，其他人呢 |
| … | | ≤26% | | |

**61 個追問輪裡有 4 筆（6.6%）重複率 ≥ 40%**，最嚴重的一筆是 6042 字有 80% 是重讀。
形狀很一致：**短的、指涉前一輪的追問**（換人／再一次／還有／除了…之外）。自足的長提問不會觸發。

**Unit 1 做完之後的修正**：只看重複率會把兩種不同的東西混在一起。加上「最長逐字重複片段」
（`longest_run`）之後分得開：

| ratio | longest_run | req | 提問 | 判讀 |
|---|---|---|---|---|
| 0.80 | **2654** | `e4147c25` | 換 蔡雨築 是否同樣的結論說明。 | 整段搬運 |
| 0.72 | **369** | `c4f3f3b3` | 還有其他建議嗎 | 整段搬運 |
| 0.68 | 69 | `896b2143` | 再一次排序。 | 逐句改寫 |
| 0.52 | 31 | `ffe409c4` | 除了 蔡雨築 之外，其他人呢 | 逐句改寫 |

**真正「把前一輪整段搬過來」的是 2 筆，不是 4 筆。** 另外兩筆是順著同樣的次序把同一批人
重講一遍——同一份特質資料寫出來的句子本來就會像，那一類不見得是缺陷。E-16 要修的是前者，
所以基線要記成 **2/61**，`[前輪脈絡]` 區塊的效果也要看這個數字。

（共同片段是**保序**的——`SequenceMatcher` 找的是最長共同子序列，不是集合交集——所以高
ratio 代表「順著同樣的次序重講一遍」，不只是「用了同一批詞」。把段落順序整個對調，ratio
會掉到 0.1 以下。）

**根因**：payload 裡沒有任何一句話說「前面那些已經在使用者畫面上了」。

`prompts.log` 的 `[CONVERSATION HISTORY]` 是 `oldest first, verbatim`，`c4f3f3b3` 那一輪帶了
**10 則訊息、12839 字**的完整前文，接著 user message 是：

```
[本輪判讀對象]
共 10 位：…
以本節為準；先前對話若提到其他人選，一律不再視為本輪對象。

[任務指令]
還有其他建議嗎
```

模型看到的是「五份完整報告 + 一句五個字的提問」，而 System 規範第 6 條又要求**每次回答**
文末都要附結語句——整個 payload 都在暗示「每一輪都是一份完整的報告」。在這個框架下，
「還有其他建議嗎」被讀成「再寫一份，並且多加幾點」是合理的。

**修復方式：加一個 `[前輪脈絡]` 區塊，沿用 `[本輪判讀對象]` 的手法**

- **只在有歷史時加**（`history` 非空），放在 user message 內、`[任務指令]` 之前。
  位置的理由跟 Unit 1 一樣：messages 的順序是 system(資料) → history → user(指令)，
  要壓過歷史就必須放在 user message 裡，放進【輸入數據】會被歷史隔開。
- **不動 `[任務指令]`**。`free_form_input_contract` 明定它等於 user_query 原文，所以這是
  一個平行的具名區塊——與 B-5 同一個模式，一併知會客戶。
- 措辭要約束「不要重新輸出已經給過的內容」，**不是**「不要談同一個主題」：
  「換成蔡雨築來看」本來就該用同樣的結構分析另一個人，把它一起擋掉會變成答非所問。

  > `[前輪脈絡]`
  > 以上對話中的回答，使用者已經看過了。本輪只需回答新的提問，不要重述、改寫或重新輸出
  > 先前已經給過的內容；必要時以一句話帶過即可。若本輪要換一個對象或換一個角度，
  > 請直接就新的對象或角度作答。

- **同時把重複率寫進稽核（只記錄）**：`repeat`——與 `focus`、`stated_count` 同一種紀律。
  這是唯一能證明區塊有沒有用的東西。**（Unit 1 已完成，見下。）**

**Unit 1 已完成（2026-09-09）**：`api_v2/services/repeat_detect.py` 量出
`{ratio, longest_run, prev_chars, chars}`，由 `packed_chat.finish()` 寫進稽核的 `repeat`
欄位；量測包在 try 裡，失敗只寫一行 warning，不影響請求。
`scripts/verify_repeat_detect.py` 釘住量測行為與「沒有被接進判定」（`completeness_check`／
`segment_gate`／`log_pipeline` 都不得引用它）。

用**生產版的同一支函式**重放全語料 61 個追問輪，數字與離線量的一致（0.80／0.72／0.68／0.52，
4 筆 ≥ 0.40，其中 2 筆 `longest_run` ≥ 300）。之後只要比同一個數字就知道區塊有沒有用。

**為什麼不用其他解法**：

- *事後偵測再刪掉重複段落*：串流已經釋出的段落收不回來（丙-3），使用者早就讀到了。
- *縮短歷史*：「換成 X 來看」這種提問需要前一輪的結構才答得對，砍歷史會讓它答不出來。

```
[前輪脈絡]
以上對話中的回答，使用者已經看過了。本輪只需回答新的提問，不要重述、改寫或重新輸出
先前已經給過的內容；必要時以一句話帶過即可。若本輪要換一個對象或換一個角度，請直接
```

三個 user message 內的區塊，順序是 `[前輪脈絡]` → `[本輪判讀對象]` → `[任務指令]`：

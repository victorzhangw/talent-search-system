- **怎麼驗**：在同一個 session 內先問一輪 N 人、再加人到 N+1 人後追問，看新增的那位有沒有進入回答。

## B. 待客戶裁定（前置未決，依 Playbook §5 不得開工）

### B-1　band 語意標籤由「整詞禁止」改為「構念式用法才禁止」

- **單元**：Unit 4b-1｜**性質**：放寬 a規範甲-2
- **為什麼要改**：出口掃描器 79%（152/193）的命中來自 band 語意標籤，而 266 個標籤裡 **61% 只有 4 個字**，豁免名單只有 4 個。命中排行第一的「需要確認」（14 次）同時是使用者自己在問題裡寫的字：「面談時還**需要確認**哪些能力或實際經歷」。
- **建議做法**：套用詞表自己已定義的 `everyday_words_rule`（`標籤 + (?=[偏程度分高低強弱]|傾向|指標|區間)`）——這條規則目前只套用在 trait 名稱上，沒有套用到 label。
- **不改的後果**：模型每答一次就要為這些日常用語跑一次改寫，是延遲與段落重複的最大來源。

### B-2　`hr_decision` 前綴改為必填

- **單元**：Unit 4b-2｜**性質**：放寬 a規範乙-8
- **現況**：規則是 `(建議|不建議|不予|予以)?\s*(錄取|…|晉升|…)`，前綴**可選**，所以任何「晉升」都命中（16 次）。已確認至少一次誤判：「多少人晉升為儲備主管」——那是正常的面談建議，而且使用者的提問裡就寫著「輔導員工並培養儲備主管」。
- **建議做法**：前綴改為必填。

### B-3　system prompt 第 17 條的範式句與詞表自相矛盾

- **單元**：Unit 4b-3｜**性質**：修改客戶正本
- **問題**：`prompts/log_system_prompt.txt:40` 第 17 條要求模型寫「此非指其**不誠實**，係自述資料宜搭配行為事例佐證」，而 `exit_scanner_wordlist_v6_2.json:47` 的 `integrity_verdict` 硬規則（無日常語豁免）禁止「不誠實」。模型照做 → 被擋 → 改寫 → 又照做 → 放棄 → 整串截斷。`4de8be30` 就是這樣掛的。
- **兩個解法擇一**：改第 17 條的範式句用字；或把「不誠實」自 `integrity_verdict` 移除。前者動客戶正本，後者動攔截規則，都需要客戶點頭。

### B-4　SPA 跨題庫特質是否採用

- **來源**：Unit 6 未處理的部分｜**性質**：產品決策
- **現況**：SPA 只定義 18 個特質，但廠商的 SPA 報告帶 **61 個**；其餘 43 個的名稱存在於 DB，但掛在 ANI/CIA 底下。`respondent_adapter` 把查詢限制在 `trait_id LIKE '{abbrev}_%'`（這個限制本身是對的——DB 有 24 組跨專案同名構念，不限制會隨機抓到別的專案）。
- **實際影響**：語料中候選人 97 的一份報告因此丟掉 43 個特質（`4de8be30` / `110a4d78`）。
- **要裁定的**：跨題庫採用是否可接受。band 校準基準不見得共用——同一個構念在 ANI 與 SPA 的分數分布可能不同，直接套用等於把另一份測驗的常模用在這份測驗上。

### B-5　Unit 1 的規格增補（知會，非裁定）

- **內容**：`question_injection_table_v9.json` 的 `free_form_input_contract` 明定「`[任務指令]`＝user_query 原文」。Unit 1 維持該句成立（指令本身一字未改），但在它前面新增了一個系統產生的 `[本輪判讀對象]` 區塊。

## D. 已知限制（刻意接受，不打算修）

這些不是待辦，是**已經決定要承擔的取捨**。寫在這裡是為了避免日後把它們當成新發現的 bug 重新調查一次。

### D-1　抓不到「名字都列了，但列在『這些人沒有資料』的句子裡」

- **單元**：Unit 2
- **例子**：`4920eef8` 的回答寫「僅有 Howard Hsu 一位具備完整資料；其餘受測者（邱佳玲、陳冠享、…）皆未包含可供分析的內容」——八個名字都在，覆蓋率檢查因此判定通過。
- **為什麼接受**：那是模型謊報資料缺席，屬於另一種檢查。改用「要有獨立標題」當判準可以抓到它，但會在 29 筆多人回覆裡造成 9 筆誤判（表格式、依主題分段的回覆）。該筆的根因（歷史蓋過名單）由 Unit 1 處理。

### D-2　自稱豁免只認同一句內的第一人稱

- **單元**：Unit 2
- **規則**：`我是`／`我叫`／`本人` + 20 字內 + 姓名，不跨逗號句號；並同時掃描本輪提問與歷史中的 user 訊息。
- **抓不到的**：用其他方式表明身分的提問（例如「這是我的團隊，成員有…」）。全語料重放下誤判為 0，但這個規則是啟發式的。

### D-3　`name_forms` 取向偏寬

- **單元**：Unit 2
- **取捨**：判成「有寫到」的代價是漏掉一次真正的遺漏；判成「沒寫到」的代價是在一篇完整的回答尾巴硬接一段補充。後者對讀者傷害大得多，所以刻意偏向前者。
- **副作用**：兩位受測者若共用前兩個字（例：呂佳珍／呂佳玲），短寫法可能互相命中，導致漏抓。語料中未出現。

## E. 本次調查發現、但沒有動的技術債

依嚴重度排序。這些不在修正計畫的六個單元內，需要另外決定要不要處理。

### E-1　自由提問的一千字上限形同虛設

- **事實**：34 筆自由提問有 **32 筆超過 1000 字**，中位數 2374 字、最長 8886 字。
- **後果**：`status=manual_review` 因此成為自由提問的常態值，不帶任何可行動的訊號；而且超長屬於「補生成修不了」的失敗（append 只會更長），所以補生成永遠不會為它觸發。
- **已排除**：字數不是漏人的原因——`110a4d78` 6905 字仍把 10 個人寫完。
- **要決定的**：把上限調整成符合實務的數字，或改成只記錄不判失敗。目前這個狀態讓 `manual_review` 這個狀態值失去意義。

### E-2　`metadata['candidates']` 的歷史資料可能已被截短

- **背景**：`chat.py:449` 把 `candidates_info` 寫進 session metadata，而修好前的 `candidates_info` 是拿分頁清單過濾出來的。切換歷史對話會從這個 metadata 還原名單——所以**修好之後新產生的資料是對的，但修好之前寫進去的可能已經少了人**。
- **查證狀況**：本機 DB 有 232 個 session 帶 metadata、其中 113 個記了 candidates，人數分布 `{1: 60, 2: 49, 3: 2, 4: 1, 11: 1}`，全部 ≤ 11 人。**無法從這裡分辨「本來就只選這幾位」與「被截短過」**——截短不是「砍到 20 位」，而是「與第一頁取交集」，結果可以是任何數字。
- **要做的**：在 UAT／PRD 上比對幾個多人 session 的 metadata 與使用者記憶中的選擇。若確認有被截短的舊資料，需決定是否回填（回填的依據只有 `chat_messages` 裡的內容，不一定夠）。

### E-3　`chat.py` 的守門是單向的

- **現況**：`missing = [c for c in candidates_info if c not in trait_reports]`——只擋「`candidates_info` 有而 `trait_reports` 沒有」。反過來（`trait_reports` 有而 `candidates_info` 沒有、或 `candidates_info` 短於 `candidate_ids`）永遠不會被擋。
- **已做的**：Unit 3 在偵測到不一致時寫一行 warning（見 A-3），但**沒有擋**——當時的判斷是先觀察，不要在還沒確認前端修乾淨之前就開始擋請求。
- **要決定的**：A-3 觀察一段時間後，是否把它升級成 409。

### E-4　`handleInitialSend` 的 100ms sleep

- **位置**：`ChatContainer.vue:524`
- **現況**：`lockSelectionAndStart()` 沒有 await，只 sleep 100ms。目前**沒有壞**——`traitReportsPromise` 在 `lockSelectionAndStart` 的第一個 await 之前就同步賦值了，而 `sendMessage` 會等那個 promise。
- **問題**：它是靠巧合正確的。只要有人在 `lockSelectionAndStart` 的 `await trackTraitReportsFetch(...)` 之前插入任何一個 await，這個保證就沒了，而且不會有任何測試失敗。
- **相對的**：`handleSendQuick`（:541）早就改成 `await lockSelectionAndStart()` 了，註解裡還寫著「這是該 bug 的根因」——同一個檔案裡兩種寫法並存。

### E-5　`verify_trait_interactions.py` 不是通過性測試

- **現況**：它是**診斷報告產生器**，跑完會覆寫追蹤中的 `docs/investigations/2026-07-14_interaction_fix_verification.md`，並以非 0 退出。因此它不能納入「全部 verify 腳本全綠」的基線，每次跑完還要 `git checkout --` 還原。
- **要做的**：把它移出 `verify_*.py` 命名空間（例如改名 `report_trait_interactions.py`），或讓它輸出到不追蹤的路徑。

### E-6　出口掃描器的整體成本效益

- **數據**：45 筆請求中 **30 筆（67%）至少命中一次**，但真正的內部標記洩漏只有 **4 筆（8.9%）**。代價是 111 次額外 LLM 呼叫、延遲中位數從 18.1s 升到 24.0s（最差 69s），加上四支專門收拾改寫副作用的函式（`strip_trailing_closer`／`strip_completion_preamble`／`strip_duplicate_closer`／分隔符保留）。
- **已做的**：Unit 4a 把「標題被改寫成整段」這條路徑堵掉了（4 次事件 4 次全部造成缺陷）。
- **沒做的**：B-1 與 B-2 才是把命中率從 67% 降下來的關鍵，兩者都要客戶認可。
- **不建議做的**：整個拿掉。它是客戶合約控制項（a規範甲，2026-08-05 還為它做過裁定），而且那 4 筆真洩漏（`RESP_03` 被抄進標題、裸分數、「連動」）都是在 prompt 已明令禁止的情況下發生的——沒有 backstop 就會直接進到 HR 使用者的畫面。留著出事是可讀性瑕疵，拿掉出事是不可逆的對外洩漏。

### E-7　無效 token 會靜默退回一個寫死的帳號，並回 HTTP 200 + 空資料

**這是本輪 PRD 實測新發現的，不是本次修改造成的。嚴重度：高。**

`routes/candidates.py:24`、`routes/init_proxy.py:11`、`routes/reports.py:35` 三處都寫著同一個模式：

```python
user_email = "eva@wepredict.io"          # Default fallback
...
decoded = jwt.decode(incoming_token, options={"verify_signature": False})
user_email = decoded.get('email', user_email)
```

token 解不開時（過期、格式錯、`Bearer null`），不回 401，而是**拿這個寫死的 email 去打上游**。實測（PRD）：

```
Authorization: Bearer null
  POST /api/v2/reports/batch  -> HTTP 200  success:true  2 份報告，每份 traits=0
  GET  /api/v2/candidates/    -> HTTP 200  success:true  回的是「另一個企業」的 2 位候選人
                                           （真實使用者有 497 位）
```

**為什麼嚴重**：widget 的 token 只有 **2 分鐘**。使用者開著頁面放一下再點「鎖定」，`fetchBatchTraitReports` 就可能帶著過期 token 送出——拿回 6 份 `traits: []`，前端判定成功、`traitReportsState` 變成 `ready`，`chat.py` 的守門因為 key 都在也放行；接著 `from_trait_reports` 因為 `scores` 是空的把每個人都丟掉，`try_packed_stream` 回 None，整個請求悄悄退回舊路徑。

**使用者看到的就是「資料好像少了」而畫面上一切正常**——與原始回報的四個症狀同一類。

**怎麼發現的**：`verify_active_roster_live.mjs` 第一次跑時 6 份報告的 traits 全是 0。原因是 harness 沒設 `userToken`，送出 `Bearer null`——假資料測試永遠測不到這個，因為它不打真後端。

**建議**：三處的 fallback 改成回 401。若擔心相容性，至少在 `reports.py` 回報「解不開 token」時不要回 `success: true`。

### E-8　改寫率不降反升：每段 0.202（0904 基線 0.087）

本輪 5 個請求、99 段、**20 次改寫**，每段 0.202；0816–0904 的 45 個請求、1272 段、111 次改寫，每段 0.087。**高了 2.3 倍。**

命中詞：`高度自律`×4、`高度信任`×4、`直接對抗`×3、`流程有序`×2、**`不誠實`×2**、`卓越進取`×1…

兩件事：

1. 這一輪的回答是「每人一個段落 + 適配優勢 / 風險」的結構（8 人），band 語意標籤出現的機會本來就比較多。所以升高有一部分是題型差異，不完全是退步。
2. **`不誠實` 仍然命中 2 次**——B-3 的自相矛盾還活著，而且是在正常提問下自然發生的。這一輪運氣好（改寫都成功了），`4de8be30` 那次就沒這麼幸運。

**這是 B-1／B-2／B-3 該做的直接證據**：20 次改寫等於 20 次額外的 LLM 呼叫，全部發生在 5 個請求裡（平均每個請求 4 次），而其中沒有任何一次是真正的內部標記洩漏。

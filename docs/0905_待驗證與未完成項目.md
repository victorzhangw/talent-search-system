#### 步驟 3 的更正：要先「最小化」，不是直接 F5

原本寫的是「按 F5 重新整理 → 仍是 6 位」。實測直接 F5 之後**名單整個不見**（連晶片都沒有）。
查下去發現不是 widget 的問題，是 demo 外殼 `App.vue` 的 `toggleChat` 設計：

- 只有**最小化**（`handleMinimize`）會寫 `traitty_widget_has_active_session` 旗標；
- **關閉**（`handleClose`）會清掉它；
- 下次點啟動器時，沒有旗標就視為「全新開始」，主動清掉
  `traitty_session_active_ids` / `traitty_selected_candidates` / `traitty_batch_reports` 等五個 key。

直接 F5 時 widget 是開著的（沒最小化過），所以旗標從來沒被寫入，重開就被當成新的一輪。
sessionStorage 在重新整理後其實還在（實測讀得到 `[58,59,65,81,82,84]`），是被外殼清掉的。

**照設計的路徑重測——最小化 → 重新整理 → 重開——通過**：晶片回到「選定 6 位人選」，
四位不在重新載入那一頁上的人也都回來了。這正是 Unit 5 要證明的事（舊做法在這裡只會剩 2 位）。

所以 A″-1 的步驟 3 應該改寫成「最小化 → F5 → 重開啟動器」。這也和 demo 首頁自己列的測試
步驟一致（最小化 → 跳轉 → 返回 → 重開）。

### E-1　自由提問的一千字上限形同虛設

- **查證狀況**：本機 DB 有 232 個 session 帶 metadata、其中 113 個記了 candidates，人數分布 `{1: 60, 2: 49, 3: 2, 4: 1, 11: 1}`，全部 ≤ 11 人。**無法從這裡分辨「本來就只選這幾位」與「被截短過」**——截短不是「砍到 20 位」，而是「與第一頁取交集」，結果可以是任何數字。

### E-7　無效 token 會靜默退回一個寫死的帳號，並回 HTTP 200 + 空資料

**狀態：已修正（2026-09-06）。** 實際是**五處**不是三處——`candidates.py` 有三個路由各寫了一次。
全部改成「解不開就回 401 `UNAUTHORIZED`」，共用 `api_v2/utils/request_identity.py`，
不再有預設身分。證據：`scripts/verify_request_identity.py`（5 端點 x 4 種壞身分 = 20 條、
原始碼不得再出現該 email、合法 token 五個端點都不是 401、helper 本身回值），全綠；
`verify_upstream_env` / `verify_typewriter_meta` / `verify_report_gate` 重跑仍全綠。
**沒有一併做的**：驗簽章與驗 exp（見 E-11）、`rag_engine` 的寫死 email（見 E-9）、
簽上游 token 時沒帶環境（見 E-10）。

**以下為當初的記錄，保留備查。**

**這是本輪 PRD 實測新發現的，不是本次修改造成的。嚴重度：高。**

`routes/candidates.py:24`、`routes/init_proxy.py:11`、`routes/reports.py:35` 三處都寫著同一個模式：

```python
user_email = "eva@wepredict.io"          # Default fallback
...
decoded = jwt.decode(incoming_token, options={"verify_signature": False})
user_email = decoded.get('email', user_email)
```

token 解不開時（過期、格式錯、`Bearer null`），不回 401，而是**拿這個寫死的 email 去打上游**。實測（PRD）：

```
Authorization: Bearer null
  POST /api/v2/reports/batch  -> HTTP 200  success:true  2 份報告，每份 traits=0
  GET  /api/v2/candidates/    -> HTTP 200  success:true  回的是「另一個企業」的 2 位候選人
                                           （真實使用者有 497 位）
```

**為什麼嚴重**：widget 的 token 只有 **2 分鐘**。使用者開著頁面放一下再點「鎖定」，`fetchBatchTraitReports` 就可能帶著過期 token 送出——拿回 6 份 `traits: []`，前端判定成功、`traitReportsState` 變成 `ready`，`chat.py` 的守門因為 key 都在也放行；接著 `from_trait_reports` 因為 `scores` 是空的把每個人都丟掉，`try_packed_stream` 回 None，整個請求悄悄退回舊路徑。

**使用者看到的就是「資料好像少了」而畫面上一切正常**——與原始回報的四個症狀同一類。

**怎麼發現的**：`verify_active_roster_live.mjs` 第一次跑時 6 份報告的 traits 全是 0。原因是 harness 沒設 `userToken`，送出 `Bearer null`——假資料測試永遠測不到這個，因為它不打真後端。

**建議**：三處的 fallback 改成回 401。若擔心相容性，至少在 `reports.py` 回報「解不開 token」時不要回 `success: true`。

### E-11　路由仍然不驗 token 的簽章與效期

**狀態：已修正（2026-09-06）。** 依裁定，前端改成**每次呼叫 API 前先 `/auth/login` 換一張新
token**（`useChatLogic.js` 的 `authFetch`，10 個呼叫點全部改用它），後端才收得緊：
`request_identity.resolve_user_email()` 現在驗簽章、驗效期、驗 aud，過期回 `TOKEN_EXPIRED`、
其餘回 `UNAUTHORIZED`；`chat.py` 那段重複的驗證也收斂到同一個 helper。
證據：`verify_fresh_token.mjs` 17 條（每個帶身分的請求前面都緊接著一次 login，且用的是那一次
換到的 token）、`verify_request_identity.py` 61 條（含偽造簽章／錯 aud／過期 × 6 個端點）。
**代價**：每個請求多一次 `/auth/login` 往返，而 login 本身會打上游驗帳號——這是這個做法的
固有成本，記在這裡以免日後當成效能退步重查。
**線上實測（2026-09-06）**：收緊之後對 PRD 跑完整流程，登入 → 候選人 → `reports/batch` →
`/chat/` SSE 全部 200，沒有出現任何 401，5 次提問都拿到回答。見 A‴ 節。

**以下為當初的記錄，保留備查。**

E-7 只拿掉「預設身分」，沒有改成驗簽——`user_email_from_request()` 仍是
`verify_signature: False`。因此偽造一張 `{"email": "別人"}` 的 token 仍可讀到別人的資料。

**為什麼沒一起做**：`/auth/login` 的 token 只有 2 分鐘，而 widget 登入時取一次就一路用到
底（`useChatLogic.js` 的 `userToken.value` 從不更新），直接開驗 exp 會讓正常使用者在
兩分鐘後全部被擋。`/chat/` 之所以驗得起來，是因為它**每次提問前都重新登入換一張新
token**（`useChatLogic.js:1185`）。

**要做的**：先讓前端會換 token（或把 login token 的效期與用途分開），再把這些路由收緊到
驗簽 + 驗期。順序不能反。

**嚴重度：高，但要動前端**——所以是一個單元，不是一行。

### E-12　點名式提問會被補生成硬接上使用者沒問的人

**狀態：已修正（2026-09-07）——採「降級為只記錄」。**

自由提問的「漏人」不再進 `appendable_reason()`，所以補生成不會為它觸發；
`missing_respondents` 照樣寫進稽核、`reason()` 照樣說得出是誰、status 仍是 failed
（因此落在 `manual_review`）。題庫題不受影響（指令明定每人一段，補生成補得對）。
改的是 `completeness_check.py`：`CompletenessResult` 多一個 `respondents_appendable`
旗標，`finalize()` 設成 `self.question is not None`。

**為什麼選這個做法**：傷害來自「自動硬接」，不是來自「判定漏人」。要恢復自動補，前提是
覆蓋率檢查先學會「使用者這輪只問了誰」——那需要點名偵測、排除語、泛稱、追問繼承四條
規則，其中「追問繼承」還需要一個跨輪的焦點狀態（現在的檢查是無狀態的），並非一個條件
的事。在那之前，寧可少補也不要硬接：少補的代價是使用者再問一次，硬接的代價是每一次
點名提問都拿到不要的內容。

**線上證據**（S8 對 UAT 連跑三次，同一批人、同樣四個問題）：

| 執行 | `retry_count.completeness` | 回答字數 |
|---|---|---|
| `uat-s8-151723`（修正前） | 1, 1, 0, 1 | 5762 / 5909 / 2170 / 5074 |
| `uat-s8-155042`（修正前） | 1, 1, 0, 1 | 2964 / 1489 / 1831 / 2377 |
| `uat-s8-155446`（**修正後**） | **0, 0, 0, 0** | 1151 / 1339 / 2142 / 1297 |

點名的三輪（1／2／4）修正後都是「回答另外提到（沒有其他人）」——只寫使用者問的那位。
第 3 輪（不點名的追問）仍然寫到全部五位，但那是**模型自己的選擇**，不是我們接上去的
（`completeness` retry = 0）。

離線：`verify_completeness_check.py` 新增四條斷言（自由提問 appendable_reason 為空、
reason() 仍說得出、status 仍 failed、稽核仍記得到），並釘住「題庫題不受影響」。

2026-09-07 第一次重跑（`155042`）跑的還是舊碼，白花 4 次額度才發現。改完務必重啟後端。

**以下為當初的記錄，保留備查。**

**2026-09-07 由 S8 劇本發現。嚴重度：高（直接改變使用者拿到的答案）。**

Unit 2 的覆蓋率檢查假設「每一則自由提問都是在問整個名單」。使用者一旦點名——
「請**只針對** X 說明」——模型正確地只寫 X，檢查卻判定「漏了其他四位」，補生成就把
那四位接在後面。實測：5887 字的回答裡約 79% 是使用者沒問的內容，而且它們有 `###` 標題，
和前半段的行文格式明顯不同。

**為什麼不是把覆蓋率檢查拿掉**：它擋的是真的漏人（`43c1f019` 漏掉游璧碩那類），
那個問題是這次修正計畫的起點。要動的是**期待覆蓋的範圍**，不是檢查本身。

**建議做法**：提問裡出現名單上的姓名時，把期待覆蓋的集合縮成「被點到的那幾位」。
比對用的 `name_forms` 已經存在（`completeness_check.py`），現在只用在回答上，
沒有用來掃提問。判準要留意兩件事：

1. 只有**點名**才縮小，泛稱（「這幾位」「他們」）維持整個名單；
2. 不點名的追問（S8 第 3 輪的「他」）靠的是歷史，不能只看這一輪的提問字面——
   S8 第 3 輪沒有觸發補生成，但那是模型自己寫全了，不是檢查判對了。

**要決定的**：這是產品行為（使用者問一位，要不要給他五位），建議連同 B 類一起讓客戶
知道，但實作本身不需要客戶點頭——它沒有動任何 a規範的攔截規則。

# Chat 對話歷史紀錄 UX 升級與優化計畫

## 1. 痛點與現狀分析
目前（2026/03）的系統中，當使用者點擊左側「歷史對話紀錄」時，系統會直接將歷史紀錄覆寫到當前正在進行的聊天畫面（即覆寫了 `messages` 變數）。

這產生了嚴重的 UX（使用者體驗）衝突：
- **視覺與操作脫鉤：** 畫面底部的「鎖定人選（Candidates）」仍停留在當前最新的選擇，但中間的訊息區塊卻變成了過去的對話內容！使用者會誤以為自己是在對著原本的候選人提問，但實際送出的對話脈絡可能已經完全錯亂。
- **原始對話消失：** 一旦點擊了歷史紀錄，原本打到一半的字或是剛剛正在進行的新對話內容就會被立刻洗掉，並且無法被存查與恢復。

---

## 2. 解決方案 A：卡片式右側滑出預覽（Read-only Preview）🌟 **(當前實作)**

**概念：完全分離「預覽狀態」與「進行中的對話狀態」。**
將歷史對話紀錄定義為「唯讀預覽」，不干涉當前的主對話區。

### 實作要點（UI/UX）：
1. **資料解耦：** 前端在 `ChatContainer` 底下切分兩個訊息陣列：`messages`（主畫面用）與 `previewMessages`（預覽卡片用）。
2. **預覽面板：** 點擊歷史紀錄不再覆寫 `messages`，而是喚起一個獨立的 `<HistoryPreviewPanel />`（或純右側抽屜），利用滑動動畫進入畫面。
3. **唯讀性：** 右側的預覽紀錄卡單純供使用者展示歷史資訊，僅配置「關閉 X」按鈕並提供滾動條。關閉後使用者隨即無縫回到目前的對話狀態繼續工作。
4. **優勢：** 前端邏輯獨立且無須更動後端 API。既能滿足查閱過往資訊的需求，又保留了當下工作狀態的連貫性。

---

## 3. 面向未來的解決方案 2：動態上下文接續（Context Switching）

**概念：讓使用者不僅能查閱，還能直接把歷史紀錄「切換成目前的對話」，就像通訊軟體回覆舊訊息群組一樣。**

### 實作要點與升級前置準備：
這個方案將會在方案 A 的預覽卡片基礎上進行升級，主要加入「接續此對話（Resume Chat）」按鈕。按下後：

1. **前端動作：**
   - 關閉預覽卡片。
   - 將 `previewMessages` 內的內容，完全覆寫蓋上 `messages`。
   - 更新目前的 `sessionId` 使其追蹤至該歷史對話的 ID。
   - *（核心重點）*：必須自動綁定並還原底部的「鎖定人選（鎖定 X 位人選的按鈕名單）」，使其變回當時對話參與的受測者陣列。

2. **後端 API 配合確認（未來改進事項）：**
   - **Session 延續能力：** 當前端以舊有的 `Session ID` 戳 Chat API 提問時，後端 LLM 和資料庫必須能精準備份與 append 該訊息至舊對話中，而不是預設開啟新的 Session。
   - **候選人（Candidates）資訊回傳：** 目前後端提供的歷史紀錄列表中（或是獲取紀錄的 Response body 裡），如果尚未帶有該筆對話的參與者（Participants/Candidates ID），後端需要擴建此欄位。唯有如此，前端在接續舊對話時才能精準抓出當時究竟是鎖定了哪些人，並掛載回畫面上。

### 結論
我們現階段採用**方案 A** 進行前端視圖隔離。既防呆，又無須仰賴後端修改即能上線；當未來後端具備了上下文及綁定人選還原的欄位支援後，即可在預覽卡片下方快速補上「接續對話」按鈕以無痛轉換為**方案 2**。

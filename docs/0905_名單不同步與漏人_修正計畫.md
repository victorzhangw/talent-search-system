## 0. 使用者回報的四個症狀

1. 勾選 8 位，結果只分析 7 位。
2. 繼續對話之後，選定的人選會變少（6 位剩 2 位）。
3. Howard 每次都有勾選，卻消失在對話中、沒有被分析。
4. 連續提問時增加或減少人選，回答仍沿用上一輪的人，不會更新。

## 1. 根因（三輪調查的最終結論）

### 1.1 症狀 1 / 3 / 4 是同一個 bug：名單變動時，歷史壓過 payload

全部語料中，**同一 session 內名單發生變動的請求只有 2 筆，2 筆全部失效**：

| req | session | 變動 | 結果 |
|---|---|---|---|
| `43c1f019` | `b004c655` | 7 位 → 8 位，新增 `704` 游璧碩 | 回答漏掉的正好只有游璧碩 |
| `4920eef8` | `1a534fca` | 1 位 → 8 位，新增 7 人 | 回答宣稱「僅 Howard Hsu 一位有資料，其餘七位皆無」 |

其餘 17 筆「有歷史但名單沒變」的多人回覆，**一筆都沒漏人**。

機制：`log_assembler.assemble()` 在自由提問（`question is None`）時，`[任務指令]` 就是使用者原句，payload 裡沒有任何一句話宣告「本輪判讀對象是這 N 位」。而 `rag_engine.load_history()` 會把最多 `MAX_HISTORY_TURNS=6` 輪的完整前文夾在 system 與 user 之間，前文裡的舊名單在 recency 上勝過資料區。

> 調查過程中曾出現一個錯誤結論：「有歷史就有 32% 機率漏人」。該統計把**提問者本人**（`6b94b4f4` 的 Victoria、`7569af1e` 的鄭皓仁，提問開頭都是「我是…」）誤算成被漏掉的分析對象。剔除後真正漏人只有上表 2 筆。此註記保留，避免後續再犯。

### 1.2 沒有任何檢查會攔住漏人

`completeness_check.py:257`：

```python
if self.question is not None and len(self.respondents) > 1:
    result.missing_respondents = [...]
```

自由提問 `question is None`，這段整段跳過。語料中 34 筆自由提問全部 `missing_respondents=[]`、`completion=0`——不是「檢查過都在」，是「從未檢查」，補生成一次都沒觸發過。

（附帶事實：34 筆自由提問有 32 筆超過 system prompt 第 5 條的一千字原則，中位數 2374 字、最長 8886 字。但超長的回覆照樣可以把 10 個人寫完（`110a4d78`：6905 字、10 人全到），**字數不是漏人的原因**，不列入本次修正範圍。）

### 1.3 後端不以請求的名單為準

`packed_chat.try_packed_stream()` 的受測者名單來自 `trait_reports.keys()`，而 `trait_reports` 是前端整包 sessionStorage 快取。前端送來的 `candidate_ids` 才是完整且正確的本輪名單，後端目前**完全沒有使用它**。

### 1.4 症狀 2：鎖定名單用分頁清單過濾

`useChatLogic.js:244`：

```js
const activeConversationCandidatesObjects = computed(() =>
    candidates.value.filter(c => idIncludes(activeConversationCandidateIds.value, c.candidate_id)))
```

`candidates.value` 是分頁清單（`PAGE_LIMIT = 20`），`fetchCandidates(false)` 是整個取代（:777）。三條還原路徑（重新整理 :699／開新分頁 :673／切換歷史對話 :538）都只還原 ID、不還原人物件。`traitty_selected_candidates` 這個 key **寫 4 次、刪 2 次、讀 0 次**，是死資料；`openNewTab` 存進 localStorage 的 `state.selectedCandidates`（:281）同樣從未被讀回。

連帶影響：`sendMessage` 的 `candidates_info`（:1033）用同一個 filter，會被截短；`chat.py:352` 的守門只檢查 `candidates_info ⊆ trait_reports`（單向），截短永遠不會被擋；`chat.py:449` 又把截短的名單寫進 `metadata['candidates']`，下次還原歷史對話會越還原越少。

> 註：`candidates_info` 被截短時，`respondent_adapter.from_trait_reports` 會讓姓名退化為 `Candidate-<id>`。全部語料 grep 結果為 **0 次**，屬**潛在缺陷、尚未發生**。修 Unit 5 即可根除。

### 1.5 出口掃描器的改寫會複製整個段落

改寫長度變化（n=32）：內容縮水 0 筆、長度相近 27 筆、**大幅膨脹 5 筆**。膨脹的那幾筆全是「只有標題的一行」被命中：

```
110a4d78 seg51   24 字 -> 1270 字  (5292%)
c5e0ef45 seg17   26 字 ->  779 字  (2996%)
fc94296d seg16   34 字 ->  932 字  (2741%)
4de8be30 seg3    35 字 ->  737 字  (2106%)
```

標題被丟去改寫，改寫器拿著整份 payload，回傳的是「標題＋整段內容」；接著模型自己原本要寫的那段內容也照常串流進來、也被釋出。**使用者讀到同一段兩次。** 已實地確認 `fc94296d`／`c5e0ef45`／`110a4d78` 三筆交付回覆的面談段落重複，`4de8be30` 則是改寫兩次仍不過而整串截斷。**這 4 次事件 4 次全部造成缺陷。**

觸發詞排行第一的是 **「需要確認」（14 次）**——它是 band 語意標籤，同時也是使用者自己在問題裡寫的字（「面談時還**需要確認**哪些能力或實際經歷」）。266 個 band 標籤裡 61% 只有 4 個字，豁免名單卻只有 4 個。

出口掃描器整體統計：45 筆請求中 30 筆（67%）至少命中一次，但**真正的內部標記洩漏只有 4 筆（8.9%）**；命中來源 band 語意標籤佔 152/193（79%）。代價是 111 次額外 LLM 呼叫、延遲中位數從 18.1s 升到 24.0s（最差 69s）。

### 1.6 規範自相矛盾

`prompts/log_system_prompt.txt:40` 第 17 條要求模型寫的範式句：

> 涉及可信度保留的句子附中性化緩衝，範式：「此非指其**不誠實**，係自述資料宜搭配行為事例佐證」

`config/exit_scanner_wordlist_v6_2.json:47` 的 `integrity_verdict` 硬規則（無日常語豁免）：

> `(表裡不一|刻意隱瞞|言行不一|虛偽|不誠實|說謊|造假)`

模型照著第 17 條寫 → 被擋 → 改寫 → 又照做 → 放棄 → 整串截斷。`4de8be30` 就是這樣掛的。

同樣問題：`hr_decision` 規則的前綴 `(建議|不建議|不予|予以)?` 是**可選**的，所以「多少人晉升為儲備主管」這種正常面談建議也被攔（16 次命中中已確認至少 1 次為此類誤判）。

### 1.7 特質資料缺陷

- `trait_definitions.ANI_02.name_en = 'Resilience1'`——全庫唯一結尾帶數字者。廠商送 `Resilience`，正規化後 `resilience` vs `resilience1` 不 match，**每位 ANI 受測者的韌性都被丟掉**。
- `CSR_23.name_en = 'Material Avoidance'`，廠商送 `Materialism Avoidance`，每位 CSR 受測者固定丟 1 個（0904 一天 17 次）。
- SPA 只定義 18 個特質，但廠商的 SPA 報告帶 61 個（其餘 43 個的名稱存在於 DB 但掛在 ANI/CIA 底下）。`respondent_adapter.py:96` 的 `trait_id LIKE '{abbrev}_%'` 限制本身是對的（DB 有 24 組跨專案同名構念），但要不要跨專案採用是產品決策。

## 3. 單元定義

### Unit 1 — 自由提問的 `[任務指令]` 前加上本輪名單宣告

**修什麼**：症狀 1／3／4 的共同根因（§1.1）。

**改哪裡**：`BackEnd/api_v2/services/log_assembler.py`

**做法**：`question is None`（自由提問）時，在 `AssembledLog.instruction` 的 `[任務指令]` 區塊**之前**，加入一個獨立的具名區塊：

```
[本輪判讀對象]
共 8 位：邱 佳玲-聯醫、陳 冠享-一站式服務、…、Howard Hsu。
以本節為準；先前對話若提到其他人選，一律不再視為本輪對象。

[任務指令]
<user_query 原文，一字不改>
```

**設計決定與理由**：

| 決定 | 理由 |
|---|---|
| 只在 `question is None` 時輸出 | 題庫題的 LOG 本體必須與 v7 範例逐行相同 |
| 新增**平行區塊**，不改寫 `[任務指令]` 內容 | `question_injection_table_v9.json` 的 `free_form_input_contract` 明定「`[任務指令]`＝user_query 原文」。新增兄弟區塊可維持該句仍然成立，與既有「歷史區塊放在 LOG 本體之外」是同一種手法 |
| 放在 user message 內、緊鄰 `[任務指令]` | message 順序是 system(資料) → history → user(指令)。放在資料區會被歷史隔開，recency 上輸給歷史；放在這裡才壓得住 |
| 只列**姓名**，不列 `RESP_xx` | `RESP_03` 被抄進標題正是 `4de8be30` 整串截斷的起因，不可再把該 token 放進指令 |
| 只宣告名單，**不要求**「每人都必須有獨立段落」 | 語料中 `6b94b4f4`（「我是 Victoria，帶領 8 人團隊」）的提問者本人不需要獨立段落，強制要求會製造誤判。覆蓋率是 Unit 2 的事 |
| 單人自由提問也輸出 | `4920eef8` 是 1 人 → 8 人的轉場，單人輪次同樣需要覆寫歷史 |

**明確不碰**：題庫題路徑；`log_system_prompt.txt`；`to_messages()` 的 message 結構；歷史載入邏輯。

**規格影響（需知會客戶）**：`free_form_input_contract` 寫的是「`[任務指令]`＝user_query 原文」。本單元維持該句成立，但在它前面新增了一個系統產生的區塊，屬**規格增補**，須向客戶說明並取得認可。

**驗收條件**：

1. `question is None` 且 1 位受測者 → `instruction` 含 `[本輪判讀對象]` 區塊，且寫「共 1 位」，並列出該姓名。
2. `question is None` 且多位受測者 → 名單順序與 payload 中 `RESP_01..RESP_NN` 的順序一致，人數正確。
3. `[任務指令]\n<user_query>` 子字串在 `instruction` 中**原文逐字存在**（契約仍成立）。
4. `question is not None`（題庫題）→ `instruction` 與改動前**完全相同**（不含 `[本輪判讀對象]`）。
5. 名單區塊**不含**任何 `RESP_\d+`。
6. `to_log_text()` 與 `to_messages()` 重組仍逐字相等。
7. `verify_log_assembler.py` 三份 v7 範例仍為 `no unexpected line differences -- 0 lines`。
8. 全部 25 支 verify 腳本仍全綠（`verify_log_assembler.py` 內的 free-form 斷言依本單元語意同步更新，屬本單元範圍）。

### Unit 2 — 自由提問也做受測者覆蓋率檢查

**修什麼**：§1.2。讓漏人被偵測到，並在可修時觸發補生成。

### Unit 4 — 出口掃描器：短段落不送改寫，band 標籤降級

**修什麼**：§1.5、§1.6。目標是把段落重複與整串截斷降到零，同時**不減損**真正的內部標記防護。

**改哪裡**：`BackEnd/api_v2/services/segment_gate.py`、`BackEnd/api_v2/config/exit_scanner_wordlist_v6_2.json`、`BackEnd/api_v2/prompts/log_system_prompt.txt`

**做法**：

1. **短段落不送改寫**：段落長度低於門檻（暫定 60 字）或整段是標題行時，不呼叫改寫器；改為就地遮罩／刪除命中的 token，遮罩後仍命中才捨棄該段。此條可獨力消除全部 4 次已知損害事件。
2. **band 語意標籤降級**：把 `band_labels_blocklist` 的判定從「整詞禁止」改為套用詞表自己已定義的 `everyday_words_rule`（`標籤 + (?=[偏程度分高低強弱]|傾向|指標|區間)`）。此規則目前只套用在 trait 名稱上，未套用到 label。

#### 4a 的做法（與原計畫第 1 項的差異）

原計畫寫的是「不呼叫改寫器，改為就地遮罩命中的 token」。實作時改用兩道防線，理由是**遮罩會把標題弄壞**：`## 四、面談時需要確認的能力與實際經歷` 遮掉「需要確認」會變成 `## 四、面談時的能力與實際經歷`，而那個誤判本身要等 4b 才會消失。兩道防線都不需要動客戶規格：

2. **撐大的改寫一律退回**（`segment_gate._overgrown`）：改寫回來的東西超過原段落 3 倍**且**多出 150 字以上，就不是這一段的改寫，而是模型另外寫了一段。當成一次失敗的嘗試處理，跟回空一樣。

#### 與計畫的差異：驗證方式改為可重複執行的腳本

原計畫寫「以瀏覽器實測 + Network payload 截圖為證據」。實際嘗試時 Chrome 擴充功能未安裝完成，瀏覽器工具不可用；只靠「build 過了」不構成驗收（Playbook §4：沒有證據＝沒驗收）。

因此改用 Node 直接驅動這個 composable——Vue 的 `ref`／`computed` 在純 Node 環境可運作，瀏覽器專屬的 `window`／`sessionStorage`／`localStorage`／`fetch` 以最小樁替代。這比截圖更好：可重複執行、可回歸。

專案的前端本來沒有測試基礎設施（§2.4 說明沿用後端的 `verify_*.py` 機制）。新增的這一支沿用同樣的命名與輸出格式（`[OK]` / `[DONE] all checks passed`），不引入任何測試框架。

#### 實作

維護點五處：`lockSelectionAndStart`、`addCandidates`、`removeCandidate`、`switchContextToPreview`、`resetAndReselect`。還原點三處改為**讀回** `traitty_selected_candidates` 與 `state.selectedCandidates`——這兩個 key 本來是寫了從不讀的死資料。`sendMessage` 的 `candidates_info` 與 `openNewTab` 的 `selectedCandidates` 也改用同一個來源。

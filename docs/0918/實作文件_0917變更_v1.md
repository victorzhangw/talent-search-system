| 檢查 | 結果 |

| INSERT 筆數 | 2918 ＝ 113 + 3 + 339 + 2389 + 74，五張表齊全 |
| 單引號未成對的 INSERT | 0 |

**關於 sequence：已查證，不需要額外處理。** 備份檔帶明確 `id` 值且**沒有** `setval`，乍看會擔心還原後主鍵撞號。實測結論是安全的，理由是：匯入器用的是 `TRUNCATE ... CASCADE`（**沒有** `RESTART IDENTITY`），所以 sequence 只增不減；本機現況 `trait_bands` 的 `max(id)=6019`、`last_value=6019`，還原寫回的是 5681–6019 這段舊 id，而 sequence 早已越過它們，下一筆取到的號不會撞。

> **唯一會撞的情境**：有人手動跑過 `TRUNCATE ... RESTART IDENTITY` 之後才還原。那不是本文件的任何一條路徑；若真的發生，還原後補一句
> `SELECT setval('trait_bands_id_seq', (SELECT max(id) FROM trait_bands));`（三張有 sequence 的表各一次）即可。

**還原演練（建議在 U4 實跑前做一次）**：建一個暫用資料庫（例如 `ai_chatbot_v2_restore_drill`），把備份檔灌進去，確認五張表筆數是 113 / 3 / 339 / 2389 / 74，然後刪掉該資料庫。這一步證明的是「備份檔真的還原得回來」，而不是「備份檔存在」——後者不等於前者。

程式面 revert commit。**回滾必須後進先出**：U2 建立在 U1 的姓名形態上、U5 建立在 U6 的資料欄位上，跳著 revert 會留下對不起來的中間狀態。

```python
"""受測者姓名的顯示形態（a §4 / b §8）。

廠商姓名欄帶格式雜訊：姓與名之間一個半形空白，後面直接黏上單位——
`邱 佳玲-聯醫`、`呂 佳珍教育訓練課`、`蘇 緯弘`。而 a §4 要求模型以真實姓名稱呼、
不得附加單位，模型也確實照做（0916 全語料：乾淨姓名命中 36 次，單位字樣 0 次）。
於是 b §8 的「姓名皆出現」若照字面比對，對帶後綴的人必然 100% 判缺。

這裡把正規化提前到打包入口：payload 看到的就是模型會寫出來的那個字串。
`completeness_check.name_forms()` 的容錯**保留不動**，那是第二道防線。
"""
```

需要提供兩個函式：

**`display_name(raw: str) -> str`**

| 步驟 | 規則 |
|---|---|
| 1 | 空字串／None → 原樣回傳 |
| 2 | 字串含 ASCII 字母 → **原樣回傳**（`Howard Hsu`、`Anne-Marie Chen` 完全不動） |
| 3 | 於首個分隔符 `-－/／_（(【[` 切斷，取前段 |
| 4 | 守門：前段去空白後長度 < 2，或「被切掉的尾段」長度 > 「保留的前段」長度 → 退回 `raw`（擋 `聯醫-邱佳玲` 這種前綴式單位） |
| 5 | 去除姓名內部所有空白 |

**必須是冪等的**：`display_name(display_name(x)) == display_name(x)`。這是驗收項，不是註解。

### 4.2.1 刻意不做「黏接式單位」的還原

`呂 佳珍教育訓練課` 這種**沒有分隔符**的單位，`display_name` 一律不動，原樣送進 payload。

理由是這件事**無法確定性判斷**：看到 `呂 佳珍教育訓練課`，我們無從得知名字是 `佳`、`佳珍` 還是 `佳珍教`。`completeness_check.name_forms()` 現有的「取名的前 2 字」是**比對用**的啟發式——它一次產生多種寫法，多給幾種的代價只是判定寬鬆一點。拿同一招來決定**顯示**姓名則完全不同：四字名（例如 `歐陽 建志豪`）會被截成 `歐陽建志`，等於系統主動把人名寫錯，再要求模型照著寫錯的名字稱呼人——比現在的誤判嚴重得多。

所以分工是：

- `display_name`（顯示）只做**可逆、無歧義**的處理：分隔符後綴、內部空白。
- `name_forms`（比對）繼續吸收黏接式單位，維持現狀不動。

黏接式單位的根治在資料源頭。建議在交付客戶的清單裡加一條：請廠商統一姓名欄格式（單位一律用分隔符，或另闢欄位）。

**`resolve_roster_names(respondents) -> bool`**

掃整份名單，若有兩人以上 `name` 相同，把**全體**的 `name` 還原成 `raw_name`，回傳 `True`（表示發生碰撞）。理由：`王小明-北區` 與 `王小明-南區` 被併成同一人的話，§8 的漏人檢查會永遠判「都寫到了」，比現在的誤判更危險。

問題：`hr_decision` 會攔 `適合擔任[^，。；]{0,8}(職|主管|經理|崗位)`。模型寫提醒時常複述題意（「關於是否適合擔任區域主管一職…」），命中後 `banned_terms()` 把命中字串丟回去叫模型別寫，模型很可能連提醒句一起拿掉——**新規則八會被攔截機制自己消掉**。

改法：

1. 模組常數：

   ```python
   ROLE_FIT_REMINDER = ('不可將AI回答用於人選擔任某職務或角色是否適任及排序順位之單一參考，'
                        '需多方驗證後決策')
   ```

2. `scan()` 開頭把答案中的提醒句換成**等長**的遮罩再掃，掃完位移不變（等長才不會讓 `Hit.start` 失真）。

   遮罩字元用 `'\x00'`，**不要用空白**：`band_code` 的樣式是 `[ABC]\s*[段屬]`，用空白當遮罩等於在答案裡插入 `\s`，有機會讓遮罩前後的字湊成一次假命中。`\x00` 不出現在任何一條 `hard_patterns`、不是 `\s`、也不在特質名／band 標籤裡。

3. `banned_terms()` 排除落在提醒句範圍內的命中。

**明確不做**：不擴充 `hr_decision` 去抓 `負責人`。目前 `是否適合擔任團隊負責人` 確實漏網，但補這個洞的方向與規則八相衝——規則八要模型**正面回應**適任類提問，放寬攔截只會增加重寫迴圈。等白名單與 U5-3 上線、觀察一輪實測資料再評估。

2. `CompletenessChecker.__init__` 決定本輪要不要查：


**動的檔案**：`BackEnd/api_v2/services/log_pipeline.py`

## 8. U2：focus 接入名單覆蓋率

### 8.1 目標

消掉自由提問點名場景的 `manual_review` 噪音，讓真正的缺漏浮出來。

### 8.2 背景實證

0916 語料 req `99489f58`：使用者只點名兩位（`蘇 緯弘`、`呂 佳珍教育訓練課`），`focus` **正確偵測到**（`source: named`、`conflict: false`），模型也正確地只寫這兩位，但 `missing_respondents` 仍列出其餘 4 位，`status` 因此是 `manual_review`。

### 8.3 動的檔案

**`packed_chat.py`**：`detect_focus()` 目前呼叫在 `LogPipeline` 建好之後、回傳 `PackedStream` 之前——也就是**串流開始之前**就已經算完了，只是算完只寫進稽核。它的輸入只有 `user_query`／名單／history／respondents，完全不碰回答，所以往前挪沒有任何阻礙。

改法是把那段往上搬到 `respondents` 建好之後、`LogPipeline(...)` 建構之前，並把 `history=pipeline.history` 換成直接用 `history` 參數（兩者同物，`LogPipeline.__init__` 只是 `list(history or [])`），再把結果傳進 `LogPipeline` → `CompletenessChecker`。

附帶效果：U1 之後 `[r.name for r in respondents]` 已是顯示形態，而使用者打的本來就是乾淨姓名，點名偵測的命中率只會變好。

**`completeness_check.py`**：`CompletenessChecker` 接受 `focus_names` 參數。`finalize()` 裡計算 `missing_respondents` 時，分母改為：

```python
scope = self.focus_names if self.focus_names else [r.name for r in self.respondents]
```

只有 `source == 'named'` 且 `conflict is False` 時才傳 `focus_names`，其餘一律傳 `None`（維持現狀）。

**明確不做**：不恢復自動補生成。維持 E-12 的結論——`missing_respondents` 照樣寫進稽核、`reason()` 照樣說得出是誰，但不自動硬接。傷害來自「自動硬接」，不是來自「判定漏人」。

### D-1　模型是否真的會照抄 `中段`　→　**已驗，結論與原文相反**

**方法**：分子分母分開量。

- 分母（曝光）：掃 61 MB `prompts.log`，數 payload 實際送出過幾次 band 段落寫法。
- 分子（照抄）：掃 725 筆稽核的 `segments[].hits`——那是**模型真的寫出來、然後被出口掃描攔下改寫**的字串，共 5442 個 segment、607 次命中。

**結果**：

| 項目 | 值 |
|---|---|
| payload 送出 `[ABC]+段` | 61 次（2 份檔案） |
| payload 送出 `[ABC]+屬` | 605 次（10 份檔案） |
| 模型輸出被攔下的 band 段落寫法 | **0** |
| 模型輸出被攔下的「含『段』」字串 | **0** |
| 中文分區（`低分區`） | 1 |

被攔下來最多的是特質名與 band 標籤（`CIA_05` 61 次、`高度信任` 30、`高度自律` 25、`晉升` 22）。

**結論**：曝光 666 次、照抄 0 次。模型從來沒有抄過 payload 裡的 band 段落寫法，`中段` 的風險比原文估計的低。

**但不能因此取消 U4-1 的防線**，兩個理由：

1. `B 段` 長得像內部代號，`中段` 讀起來是普通中文——**照抄傾向不同**，0/666 這個先驗只能部分遷移。
2. 真正的差別不在照抄機率，而在**被攔到與否**：`B 段` 就算抄了也會被攔下重寫，`中段` 抄了就直接送到讀者眼前。防線的價值在於後果，不在於機率。

**已據此修正**：U4-3 放寬 `band_code` 的優先度由「順手補洞」下修——它要補的那 3 處 `B 屬` 在 605 次曝光中被抄 0 次。仍建議做（成本近乎零、實測誤殺 0），但不是本次的關鍵路徑。

**要完全結案**（涉及真實模型）：V7 匯入前後各跑一次

```bash
cd BackEnd
PYTHONIOENCODING=utf-8 python scripts/run_packer_live.py --module mgmt_pressure   # 會花 token
PYTHONIOENCODING=utf-8 python scripts/redteam_packer.py                            # DoD 正規關卡
```

`run_packer_live.py` 用真實特質列組受測者、打真實模型；`redteam_packer.py` 是 DoD 第 4 條的紅隊關卡，會用一支獨立的掃描器重掃已釋出文字。通過標準：released 文字中 `中段` 構念義命中 0。

### D-2　佐證檢查的失敗率是否會因 02 分頁改寫而上升　→　**現有語料量不出來，需合成探針**

**先量得到的部分**：

| 項目 | 值 |
|---|---|
| `calibration_evidence_check` 適用筆數 | 50（passed 17 / failed 33） |
| 失敗率 | **66%** |
| 失敗集中在 | 2026-08-18（4/13）、08-31（2/9） |
| 2026-09-01 之後 | 幾乎全是 `n/a`——名單裡很少有人社會期望反應落 A |

佐證詞在 825 KB 回答語料中的出現次數：

| 詞 | 次數 |
|---|---|
| `行為事例` | 67 |
| `佐證` | 52 |
| `工作樣本` | 18 |
| `不以單次` | 8 |
| `交叉驗證` | **1** |
| `多方驗證` | **0** |

**兩個結論，其中一個推翻原文**：

1. **66% 的失敗率是既有問題，與 V7 無關**，而且不是「詞表沒收到模型用的詞」造成的——四個既有詞在語料裡很常見，失敗的那 33 筆是真的一個字都沒寫。原文把 U5-5 寫成能緩解失敗率，**那是錯的**，已改為「與新正本措辭對齊的低成本對齊動作，不宣稱能降低失敗率」。
2. **加 `交叉驗證`／`多方驗證` 今天幫不上忙**（語料裡 1 次與 0 次），但 V7 之後注入資料本身就寫著「資訊可信度需交叉驗證」，模型用語會跟著資料走，所以仍值得先加——它是**對未來措辭的預先對齊**，不是對現況的修補。

**為什麼量不出「是否會上升」**：09-01 之後的資料裡這項檢查全是 `n/a`，沒有可比的基準。

**結案方法（合成探針，約 4 次 LLM 呼叫）**：

1. V7 匯入**前**，用 `run_packer_live.py` 造一位 `CIA_33 = A`（社會期望反應高）的受測者，跑 2 題，記下回答是否含四個既有佐證詞。
2. 匯入**後**，同樣的題目、同樣的 band 組合再跑 2 次。
3. 比較兩組回答用的措辭。判準：匯入後若改用「交叉驗證」類措辭而不再出現四個既有詞，就證實了推論，U5-5 的詞表擴充是必要的；若措辭不變，U5-5 就只是無害的冗餘。

`run_packer_live.py` 的 `--dry-run` 可以先確認 payload 組對了再花 token。

## 1. 第一題：稱呼規範 × 全名比對

### 1.1 問題的真正形狀

衝突不在「a §4 對上 b §8」，而在**三個字串不是同一個**：

| 環節 | 實際字串 | 出處 |
|---|---|---|
| 廠商姓名欄（進 payload） | `邱 佳玲-聯醫`、`呂 佳珍教育訓練課`、`蘇 緯弘` | Traitty API `basic.name` |
| a §4 要求模型輸出 | 真實姓名，且不得附加企業／職位／身分前綴 | `a_LOG完成版模板` |
| b §8 文件寫的比對法 | 「每位受測者姓名皆出現」（字面＝全名比對） | `b_打包規則 §8` |

三者不一致，於是 b §8 若照字面實作，對帶單位後綴的人**必然 100% 判缺**。

### 1.2 實測證據（0916 PRD 語料）

- 模型輸出一律用乾淨姓名：`呂佳珍` 15 次、`蘇緯弘` 10 次、`邱佳玲` 9 次、`簡玥瀅` 2 次。
- 單位字樣（`聯醫`／`教育訓練課`／`一站式服務`／`高雄非專`）在全部回答中出現 **0 次**。
- 結論：模型自己遵守了 a §4，所以 b §8 的字面比對法一次都不會命中。

### 1.3 現況：程式已容錯，但規格沒寫

`completeness_check.name_forms()` 已經產生多種寫法（去 `-單位` 後綴、去姓名間空白、由「姓 名」還原 2–3 字本名、西文取 first name），這是 req `c5e0ef45` 的修正。0916 語料驗證有效：8 人名單中 4 位帶單位後綴，`missing_respondents` 只列出真正沒被寫到的人，帶後綴者正確命中。

**風險在於這條規則只活在程式碼裡。** b §8 仍寫「姓名皆出現」，任何依文件重寫的實作都會回歸。

### 1.4 建議做法（三層，依序）

**(A) 資料入口正規化——根治**

在 `respondent_adapter` 產生 `Respondent` 時，拆成兩個欄位：

- `display_name`：正規化後的顯示姓名。用於 payload 的 `### [受測者 | 姓名 | ID]` 標頭與 `[本輪判讀對象]` 名單。
- `raw_name`：廠商原字串。**只進稽核記錄**，不進 payload。

**`[任務指令]` 一個字都不能動**：`free_form_input_contract` 明訂自由提問的任務指令＝使用者原始提問逐字，題庫題則是題庫欄位逐字。正規化只作用在系統自己組出來的標頭與名單區塊。

正規化規則（確定性、零語意）：

1. **僅對純 CJK 姓名**套用分隔符剝除：`-`、`－`、`/`、`／`、`_`、`(`、`（`、`[`、`【` 及其後全部字元。
2. 去除姓與名之間的空白（CJK 姓名）。
3. 含 ASCII 字母的姓名**完全不動**（`Howard Hsu` 保留原樣）。
4. 無分隔符的黏接單位（`呂 佳珍教育訓練課`）：以「姓 名」的空白為界，取名的前 2 字（不足則 1 字）。

三道守門（缺一不可）：

- **前綴式單位守門**：規則 1 假設單位在後。若廠商寫成 `聯醫-邱佳玲`，剝除後會得到 `聯醫`。因此剝除結果若**長度 < 2**，或**剝除掉的尾段長度大於保留的頭段**，一律退回 `raw_name` 並寫稽核 `name_normalize_skipped`。
- **西文連字號守門**：規則 3 的存在理由就是 `Anne-Marie Chen` 會被剝成 `Anne`。判準用「字串含 ASCII 字母」，不用「是否為西文姓名」——後者是語意判斷。
- **碰撞守門**：若同一輪名單中兩位以上的 `display_name` 相同，**該輪全體退回 `raw_name`** 並寫稽核 `display_name_collision: true`。沒有這一條，`王小明-北區` 與 `王小明-南區` 會被合併成同一人，而 §8 的漏人檢查會永遠判「都寫到了」——比現在的誤判更危險。

**連帶要改的一處**：`exit_scanner` 的 `name_bound_ids` 目前是 `(r.name, respondent_id)` 配對，用來擋 `許品優（55）` 這種形狀。改用 `display_name` 後，`raw_name` 的形狀就失去防守。這組配對要**同時收兩種寫法**，不是換掉。

**連帶的好處**：`focus_detect` 與稽核的 `focus.names` 目前記的是 `呂 佳珍教育訓練課`，改用 `display_name` 後稽核直接可讀，排錯時不用再自行還原。

**(B) 規範文字同步**

- b §8 改寫：
  > 多人題另查每位受測者**顯示姓名**（`display_name`，見 §1.1 輸入正規化）皆出現且各有獨立段落。比對時忽略姓名內部空白；廠商原字串僅供稽核，不作為比對基準。
- a §4 補一句：
  > 受測者一律以系統提供的顯示姓名稱呼，不得加註單位、部門、職稱或其他身分後綴。

**(C) 程式端第二道防線——保留，不要拿掉**

`name_forms()` 維持現狀並補齊：全形／半形分隔符 `／ ＿ （`、無空白無分隔符的黏接情形。即使入口已正規化，這層仍要留著擋廠商資料格式再變。

### 1.5 客戶看到的「缺漏」還有第二個來源（需一併處理）

0916 語料 req `99489f58` 是這樣的：使用者自由提問只點名兩位（`蘇 緯弘`、`呂 佳珍教育訓練課`），`focus` 欄位**正確偵測到**（`source: named, conflict: false`），模型也正確地只寫這兩位，但 `missing_respondents` 仍列出其餘 4 位，`status` 因此是 `manual_review`。

這不是姓名比對的問題，是**點名提問時名單覆蓋率仍以全名單為分母**。`focus_detect` 已實作四條規則（點名偵測、排除語、泛稱、追問繼承）但目前「只記錄、不參與判定」。

建議第一步（風險可控）：`source == 'named'` 且 `conflict == false` 時，`missing_respondents` 的分母改為 focus 名單，**但仍不接補生成**（維持 E-12 的結論：少補勝於硬接）。這會把自由提問點名場景的 `manual_review` 噪音直接消掉，讓真正的缺漏浮出來。

## 2. 第二題：RESP_01 序號與加減人選

### 2.1 現況機制

- `log_label_for(i) = f'RESP_{i+1:02d}'`，**本次請求內的位置代號**，跨請求不保證穩定。
- 真實 `candidate_id` 完整保留在稽核的 `respondents[].respondent_id`，同一筆還有 `log_label`，對照完整。
- 代號**不會流到使用者眼前**：`exit_scanner` 的 `opaque_ids` 對 `RESP_\d+` 是硬擋；`[本輪判讀對象]` 名單區塊刻意只列姓名不列代號（req `4de8be30` 的教訓）。

### 2.2 逐項回答

**「不同 session 重複用 RESP_01」——沒有問題。**
代號永不離開 payload，稽核每筆都有 `log_label ↔ respondent_id` 對照，跨 session 一致性不具任何用途。

**「加減人選會不會有問題」——會位移，但不影響模型判讀。**
每一輪 payload 整份重建；歷史只帶純文字回答（且回答不含代號），模型沒有機會拿上一輪的號碼對這一輪的人。實際影響僅限於**人工看稽核時的混淆**。

**「是否改帶真實 candidate ID」——不建議，這是已知回歸。**
先前填的就是 `candidate_id`（`55`、`63`），模型看到 `許品優 | 55` 把數字當成姓名的一部分，寫出「許品優（55）」；出口掃描抓的是「數字＋分」與 band 樣式，括號裡的裸數字不符任何一條規則，於是原樣送到客戶眼前。改成位置代號正是為了修這個。

**「加人時編號應該繼續往下」——方向對，但真正該修的是排序來源。**
目前排序來自 `trait_reports` 的 dict 插入順序（`apply_roster` 的 `kept` 保留的是 reports 的順序，不是 `candidate_ids` 的順序）。前端只要換一條建構路徑，順序就可能整組變動。

### 2.3 建議做法

1. **排序綁定 `candidate_ids` 陣列順序**（前端送來的本輪名單順序），不再依賴 `trait_reports` 的 dict 順序。
   - 效果：名單尾端加人 → 既有人號碼不變、新人自然拿下一個號；同一份請求離線重放 → 號碼完全相同。
2. **不做跨輪續號。** 跨輪續號需要 session 狀態，會破壞「稽核可完整離線重放」這個前提（`focus_detect` 的無狀態設計正是為此），而且會讓號碼變成可累積的準識別碼，一旦洩漏影響更大。
   - 代價說明：移除名單中間的人時，後面的號碼會前移。這是同一輪內自洽的重排，稽核看得出來，可以接受。若客戶堅持「號碼永不重排」，才需要引入 session 級別的號碼登錄表——請客戶明確裁定，不要默默實作。
3. **稽核加一行人可讀對照**：`roster_map: ["RESP_01=620 邱佳玲", "RESP_02=624 …"]`。目前 `log_label` 與 `respondent_id` 同物件但沒有姓名，排錯時要再查一次。
4. **保留 `name_bound_ids` 那道防線**：即使 payload 已不含真實 ID，`姓名（數字）` 的形狀仍在掃描範圍內，防止日後有人把真實 ID 放回 LOG。

### 2.4 驗收方式

- 同一份請求重放兩次 → `log_label` 對照完全相同。
- 名單尾端加一人 → 既有人的 `log_label` 不變，新人為 `RESP_{n+1}`。
- 移除中間一人 → 稽核可讀出重排結果（預期行為）。
- 全語料重放 → 回答中 `RESP_\d+` 命中數為 0。

### 3.4 `中段` 是一個新的、不會被攔下來的洩漏字樣

V7 把 **22 列**的 `B 段屬情境敏感` / `B 屬情境敏感` 改寫成 `中段…`。從掃描器角度看，這是**倒退**：

- `band_code` 正則 `[ABC]\s*段(?!落)` 抓得到 `B 段` → 模型照抄會被攔下來重寫。
- `band_zone_zh` 正則 `[高中低](分區|分組|分群|區間)` **抓不到** `中段`。
- 結果：一個「會被攔截」的字樣被換成「會直接送到客戶眼前」的字樣。

> **風險量級校正（2026-09-18 實測）**：模型過去從未照抄過 payload 裡的 band 段落寫法——曝光 666 次、照抄 0 次（見實作文件附錄 D-1）。所以這條的優先度低於本文原本的語氣。**但仍要做**，理由由「機率」改為「後果」：`B 段` 抄了會被攔下重寫，`中段` 抄了就直接送到讀者眼前；而且 `中段` 讀起來是普通中文、`B 段` 像內部代號，照抄傾向不能直接相互推論。

不能整詞封鎖 `中段`：V7 資料裡另有 **5 處**是日常語用（`成長曲線容易在中段趨緩`、`在推進中段容易失速`、`在任務中段設確認點`、`的推進中段，安排一次確認`、`在執行中段遇到分心誘惑`），整詞封鎖會誤殺。

兩者在文本上可以乾淨分開（實測 22/22 命中、0/5 誤殺）：**構念義的 22 處全部緊接在句號或分號之後起句**，日常義的 5 處全部前接 `在`／`的`。

建議（A 與 B 同時做：A 根治資料、B 防下一版再出現）：

- **A（正本根治）**：22 列改寫成不含分區字樣的說法，例如
  `中段屬情境敏感、非固定狀態` → `此組合屬情境敏感、非固定狀態`
  `中段狀態受情境驅動，非穩定特質` → `此狀態受情境驅動，非穩定特質`
  `中段的務實平衡態度…` → `此種務實平衡態度…`
- **B（程式防線）**：`regex_pack` 新增精準改寫規則，只命中構念義：

  ```
  pattern: (?<=[。；])中段(?=情境敏感|呈|屬|狀態受|的務實)
  replace: 此組合
  ```

  並在 `exit_scanner` 的 `band_zone_zh` 加上同一組條件，**不做整詞封鎖**。

## 4. 第四題：規則八改動的影響面

新規則八＝在既有禁止句後加一條**觸發式輸出義務**：

> 當出現是否適合擔任某職位或適任排序相關提問，請務必做出提醒，告知：「不可將AI回答用於人選擔任某職務或角色是否適任及排序順位之單一參考，需多方驗證後決策」

影響面共 7 處，逐一說明。

### 4.1 出口掃描器：提醒句本身安全，但前後文會被攔

已實測跑過 9 條 `hard_patterns`：

| 測試字串 | 結果 |
|---|---|
| 制式提醒句全文 | **不命中**（安全） |
| `是否適合擔任團隊負責人，需多方驗證` | 不命中 |
| `他適合擔任專案主管` | 命中 `hr_decision` |
| `建議晉升為部門經理` | 命中 `hr_decision` |

問題在於：模型寫提醒時常會複述題意（「關於是否適合擔任區域主管一職…」），只要落進 `適合擔任[^，。；]{0,8}(職|主管|經理|崗位)` 就會命中 → 觸發重寫，而 `banned_terms()` 會把命中字串原樣丟回去叫模型別寫。模型很可能連提醒句一起拿掉，**結果是新規則八自己被攔截機制消掉**。

建議：

1. `exit_scanner` 新增精確字串白名單：掃描前先把制式提醒句遮罩，掃完再還原。
2. `banned_terms()` 排除落在提醒句範圍內的命中。
3. `hr_decision` 目前漏掉 `是否適合擔任團隊負責人`（正則的 `(職|主管|經理|崗位)` 不含 `負責人`）。**建議暫緩補這個洞**，理由是方向相衝：新規則八要求模型**正面回應**適任類提問（加提醒），而放寬 `hr_decision` 會讓模型複述題意時更容易被攔、更容易觸發重寫迴圈。先讓白名單與 4.2 的提醒句檢查上線、觀察一輪實測資料，再決定要不要補。

### 4.2 完整性檢查（§8）：目前完全沒有檢查，這是主要新增工作

新規則八的性質是「輸出必須包含某句話」，與既有的「佐證類措辭檢查」完全同型，但目前 §8 沒有任何對應檢查。**規則寫了不驗**，與 b §8 對 `expected_sections` 的態度不一致。

建議在 b §8 新增第四項「決策提醒檢查」，並維持零語意邏輯：

- **題庫題（資料驅動）**：`question_injection_table` 新增布林欄 `role_fit_reminder`。命中題的回答必須含提醒句（子字串比對，允許全形／半形標點差異）。
  依實際指令內容，建議設 `true` 的題目：

  | 題 | 理由（指令原文） |
  |---|---|
  | Q1 快速面試提問指南 | 「錄用後行動與發展建議」段 |
  | Q12 高潛人才識別要點 | 「優先投資哪位對象」「接班梯隊建議」「晉升節奏」 |
  | Q20 適合承擔的任務與專案 | 「誰和誰最合適一起分配到什麼專案」 |
  | Q21 領導風格與潛能分析 | 「儲備幹部與主管潛力評估」「企業任用與發展建議」「角色分配建議」 |

  可選（請客戶裁定）：Q15 打造高效會議團隊（「是否適合擔任主持、收斂、整合角色」）、Q22 高效溝通模式解析（「溝通角色分配建議」）。

- **自由提問（確定性詞表）**：新增 `role_fit_trigger_words`（比照 `everyday_words` 的做法，放在 `exit_scanner_wordlist` 或獨立檔）：
  `適不適合擔任`、`是否適合擔任`、`適任`、`勝任`、`排序`、`排名`、`順位`、`誰比較適合`、`哪一位適合`、`誰最適合`、`接班人選`、`升遷`、`晉升人選`、`錄取`、`優先錄用`。
  命中即要求回答含提醒句。
  這仍然是**確定性的表查找**，沒有違反 b 文件的零語意原則——與 §9 的 `everyday_words` 判定、以及 `per_person_sections` 由題庫資料回答「這題要不要逐人分段」是同一種手法：判斷留在資料裡，程式只讀不推。
  已知會過度觸發：使用者問「幫我把這些任務排序」也會命中。成本不對稱且方向有利——多觸發的代價是多一句提醒，少觸發的代價是客戶要求的合規提醒沒有出現，所以刻意選擇寧可多觸發。

- **比對方式用核心子字串，不用全句**：模型很可能寫出語意相同但標點／連接詞不同的版本。以「單一參考」＋「多方驗證」兩個詞同時出現為命中條件，比整句 exact match 穩健得多；否則會出現「模型其實寫了、檢查判缺、補生成再補一句制式句」的雙提醒。

- **不過的處置**：這一項**可以**用補生成修（尾端 append 一句即可），與「缺段落」同型，因此列入 `appendable_reason()`；不像佐證措辭與超字那樣只能 `manual_review`。
  已知副作用（可接受）：補生成接在已釋出的文字之後，而規則六的結尾句多半已經釋出，所以補上的提醒會落在結尾句**之後**。規則八沒有規定位置，可接受；但要把制式提醒句一併加進 `strip_duplicate_closer` 的去重清單（見 4.3），避免補生成同時又重寫一次結尾句。

### 4.3 與規則六的關係：兩句並存，且去重機制只認一句

規則六已要求文末固定句（「本分析旨在提供觀點與輔助…」）。新規則八是**第二句**提醒。

- a 文件需明講「兩句並存、不得互相取代」，否則模型常只留一句。
- 已實測確認：`log_pipeline.closing_sentence()` 的正則要求句子帶 `文末|結尾|最後`，規則八那句沒有這三個詞，**不會**被誤認成結尾句——這點安全。
- 但 `strip_trailing_closer()` / `strip_duplicate_closer()` **只去重規則六那句**。補生成時規則八的提醒若重複出現，沒有任何機制處理。建議把去重清單擴充為兩條。

### 4.4 與題目指令重疊：Q21 會出現三句同性質提醒

Q21 的指令自己已經各要求一句：

- 單人版：「此判讀為 Traitty 根據特質 **band** 與互動語意所做之領導傾向分析，應搭配職務要求、實際經驗、行為觀察與後續面談綜合判斷。」
- 多人版：「此分析為基於特質的領導傾向判讀，應搭配職務要求、實際表現、管理觀察與後續面談綜合判斷。」

加上規則六與新規則八，Q21 回答尾巴會有 **3 句**性質相同的提醒。

建議：刪除 Q21 指令裡的那兩句，統一由規則八的制式句承擔。

**另有一個獨立缺陷必須修**：Q21 單人版那句寫著「特質 **band**」，等於指令要求模型輸出 band 字樣，與全域規範甲-1（不得出現 band 字母）直接衝突。這句無論是否採納上面的刪除建議，都該改掉。

### 4.5 V7 的 02 分頁改動會推高佐證檢查的失敗率

§8 共同檢查要求：受測者有社會期望反應 band A 時，回答須含 `佐證／行為事例／工作樣本／不以單次` 其一。

V7 把這三個校準特質的敘述改成「…資訊可信度需**交叉驗證**」，四個詞一個都沒有。模型的用語會跟著注入資料走，所以詞表要跟著對齊。

> **2026-09-18 實測修正**：本節原本寫「失敗率因此可能上升」，語氣過強。實測顯示失敗率**現在就是 66%**（50 筆適用、17 過 33 敗），且與詞表覆蓋無關——四個既有詞在 825 KB 回答語料裡很常見（`行為事例` 67 次、`佐證` 52 次），失敗那 33 筆是真的一個字都沒寫。而 2026-09-01 之後這項檢查幾乎全是 `n/a`（名單裡很少有人社會期望反應落 A），**現有語料量不出「會不會上升」**。結案方法是合成探針：V7 匯入前後各用 `run_packer_live.py` 造一位 `CIA_33=A` 的受測者跑 2 題，比較措辭。見實作文件附錄 D-2。

建議仍為：b §8 的佐證詞表新增 `交叉驗證`、`多方驗證`，與正本新措辭對齊（`多方驗證` 同時是新規則八提醒句的用詞）。**定位是預先對齊，不宣稱能降低失敗率。**

### 4.6 c 檔刪除 L 欄（expected_sections）——本次最高風險項

客戶說明刪除理由是「該欄與多人版本快速提問產出有衝突」。這個觀察**是對的**：單人版的段落清單拿去驗多人回答，會整批判缺。

但處置方式有問題：

1. **線上不會立刻壞**——程式讀的是 `question_injection_table_v9.json`，不是 xlsx。
2. **但 xlsx 是題庫正本**。正本不再帶 `expected_sections`，等於 §8 段落齊全檢查失去正本來源。任何一次「從 c 檔重生 JSON」都會把 22 題的期望段落清空，§8 全面變成 `skipped`，而且會 log 出**錯誤的原因**：「本題未做段落齊全檢查（原因：指令未定義固定段落標題）」——實際原因是資料被刪掉了。
3. **衝突其實已經在 JSON 端解掉了**：JSON 已有 `expected_sections`（單人）與 `expected_sections_multi`（多人）兩套。刪欄是在解一個已經解掉的問題。

建議（擇一，優先 A）：

- **A**：正式宣告 `question_injection_table` 為 `expected_sections` 的唯一正本，在 c 檔的「說明」分頁寫明「段落清單不再由本檔維護，請勿由本檔重生 JSON」，並附一頁唯讀人閱對照。維護成本最低。
- **B**：c 檔改回兩欄 `expected_sections_single` / `expected_sections_multi`，與 JSON 欄名一致。

### 4.7 §8 另外三個順帶要補的資料缺口

盤點 JSON 時發現的既有缺口，與規則八無關但同屬 §8，一併列出：

1. **Q2／Q6／Q11 的 `expected_sections_multi` 是空陣列 `[]`。** 程式視為「有值但空」→ 多人模式整項跳過並 log「指令未定義固定段落標題」。但這三題的多人指令**有**明確編號段落（例如 Q2：「1. 對象間差異比對／2. 協同互補優勢／3. 挑戰拉扯／4. 發展與建議配置策略」）。應補齊，否則這三題多人模式等於沒有段落檢查，而 log 的原因還是錯的。
2. **`expected_sections_single` 這個 key 在 JSON 裡不存在。** 單人一律走 fallback，每次都 log `UNSPLIT_LOG`（「本題 expected_sections 尚未拆分 single/multi，退回使用單一欄位」）。要嘛補上 key，要嘛把這行 log 降級——目前它每一筆單人請求都會出現，稽核噪音。
3. **空值與缺值的語意要分開。** 目前「指令確實沒有固定段落標題」（Q14／Q15／Q22，正確）與「資料還沒填」（Q2／Q6／Q11）走同一條路徑、log 同一句話。建議把 `expected_sections_note` 設為必填：有 note ＝ 刻意留空；無 note 而為空 ＝ 資料缺，應 log 為 `data_gap` 而非 `skipped`。

### 4.8 System prompt 同步

runtime 的 `BackEnd/api_v2/prompts/log_system_prompt.txt` 仍是**舊版規則八**。已逐行比對 v8 範例（`07_新版LOG範例_匡列型_壓力題_v8_260917.txt`）與 runtime，差異只有三處：

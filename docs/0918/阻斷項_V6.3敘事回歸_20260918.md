## 2. 證據

### 2.1 規模

| 比對 | 清洗後不同的列數 |
|---|---|
| V6.2 → V6.3 | **1053 / 2389（44%）** |
| V6.3 → V7 | 42 |

1053 列裡有 **1007 列變短**，平均長度 **181 字 → 71 字**。

### 2.2 內容形態

| 版本 | `CIA_01_A × CIA_09_A` 的敘事 |
|---|---|
| V6.2 | 表現為「長線自持的推進者」。他對品質與進度的要求一貫，不需要外部催促也能持續把工作往前推；同時面對眼前輕鬆的誘惑，他多半能守住原本的節奏，不會為了一時舒服偏離原本計畫… |
| V6.3 / V7 | 長期目標的長跑者。具備極強的抗誘惑能力與延遲滿足感，能自主完成長期艱難任務。 |

V6.2 是行為導向、帶機率性措辭的寫法；V6.3 是構念式、帶絕對化措辭的寫法。

### 2.3 「舊版本」是查證過的，不是推測

掃 61 MB `prompts.log`，數各時期 payload 實際注入的是哪一種寫法（取三組 V6.2／V6.3 專有的敘事開頭）：

| 期間 | V6.3 式（簡略） | V6.2 式（完整） |
|---|---|---|
| 2026-03 ~ 07 | 16 | **0** |
| 2026-08-10 起 | **0** | 48 |

**V6.3 的 08 分頁文字，就是 2026-08 以前在線上跑的那一版。** 八月換成 V6.2 的完整版，0915 又換了回去。

### 2.4 絕對化措辭（全域輸出規範乙-5 明禁）

| 詞 | V6.2 | V6.3 | V7 |
|---|---|---|---|
| 極強 | 4 | **56** | 56 |
| 極度 | 13 | **90** | 90 |
| 絕對 | 2 | **14** | 14 |

規範乙-5 寫的是「一律使用機率性措辭；禁止絕對化」。這些字會住在**注入給模型的資料裡**。

**但要說清楚兩件事，免得這一項被高估：**

1. **出口掃描完全沒有規則在管這些詞。** 實測九條 `hard_patterns`，「他的抗壓性極強高」「…絕對高」「…一定高」全部 0 命中。所以不論匯入哪一版，基準測試都不會因為這件事變紅。
2. **模型本來就會寫。** 848 KB 回答語料裡：一定 138、一貫 25、絕對 18、極度 12、總是 9、極強 3。而那段語料的 payload 是 V6.2（極強 4／極度 13／絕對 2），示範量很少，模型照樣寫。

所以這一項的正確描述是：**一個既有的、沒有守門的缺口，V7 會把 payload 裡的示範量放大 7–14 倍**。它是風險，不是可被基準測試攔下的缺陷。

## 4. 最可能的成因（待客戶確認）

**02 分頁只改了 25 個儲存格。** 把 V6.2 → V6.3 的 02 分頁逐格比對（339 列 × 19 欄）：

| 欄位 | 筆數 | 改了誰 |
|---|---|---|
| `trait_name_en` | 6 | **ANI_02** 的 `Resilience1` → `Resilience` |
| `semantic_description` | 6 | 只有 `CIA_33`／`ANI_23`／`SPA_12` |
| `management_focus` | 5 | 同上三個 |
| `ai_do` | 5 | 同上三個 |
| `ai_dont` | 3 | 同上三個 |

中文名 0 筆、band 標籤 0 筆——檔名雖然叫「改特質」，113 個特質的名稱一個都沒改。
（`Resilience1` 是有意義的修正：`name_en` 以數字結尾會讓 ANI 受測者的韌性解析不到，`verify_packer_data_health` 至今留著那條回歸測試。）

**所以 0915 的意圖範圍小而明確：修一個 `name_en` 錯字、重寫三個校準特質的四欄文字。**

而同一份檔案的 08 分頁換掉了 1053 列（44%）。

**這個不對稱是最強的證據**：02 分頁明顯是在 V6.2 上改的（只差 25 格），08 分頁卻整片是 2026-08 以前的版本——**同一個檔案裡，兩個分頁來自不同的底稿**。最合理的解釋是 0915 的編輯是在一份較舊的工作簿上套用那 25 格改動。

兩項旁證指向同一個方向：

1. **客戶自己 0917 更新的 a／b 文件，內容正本欄位仍指 V6.2**（§5）。
2. **三份 v8 範例仍帶著 V6.2 的敘事**——如果 V6.3/V7 的簡略版是有意改版，範例應該跟著換。

但這仍是推論。**必須由客戶確認**，不能由實作方代為決定——這是內容正本的歸屬問題。

## 8. 若客戶確定採用 V7：如何通過基準測試

前提：客戶明確回覆「08 分頁就是要用這一版」。以下是讓 `verify_all` 從 26/31 回到 31/31 的完整路徑。

### 8.0 這一節是實測過的，不是推演

2026-09-18 在一個暫用資料庫（`v7trial`）真的跑了一遍，線上的 `ai_chatbot_v2` **完全沒有被動到**（事後確認 `trait_bands.version` 仍為 NULL、`CIA_33_A` 的 K 欄仍是 V6.3 文字）。

步驟與結果：

| 步驟 | 結果 |
|---|---|
| 建 `v7trial`、建表、以 `trait_backup_20260915_155426.sql` 還原 | **113 / 3 / 339 / 2389 / 74**，`-v ON_ERROR_STOP=1` 無錯誤。**順便完成了實作文件 §3.7 一直沒做的還原演練——備份確實還原得回來** |
| 在該庫匯入 V7（`--skip-endpoints --spec-version V7-20260917`） | `stamped=339/339`；`trait_endpoints` 74 列完整保留（「Preserving 74 rows across the truncate」） |
| `DB_NAME=v7trial python scripts/verify_all.py` | **27 / 31**（匯入前是 26 / 31） |

**`verify_calibration` 如 §8.2 預測，匯入 V7 之後自動由紅轉綠。** 剩下的正好是預測的四支。

再逐項查這四支的差異內容，確認**沒有第五個因素**：

| 腳本 | OK 項 | 失敗內容 |
|---|---|---|
| `trait_blocks` | 3 | 21 處不符中，18 處是已知的 SPA 欄名前綴（b §2 已記錄），**3 處 unexplained 全是同一件事**：`CIA_33_A` 的行為面向文字 |
| `interaction_selector` | 25 | 8 項全是 `items match verbatim`；標頭、條數、子區塊順序全過 |
| `log_assembler` | 53 | 34／92／85 行差異，抽樣全是索引行 K 欄與交互敘事本文；三個 `[NOTE]` 是腳本本來就容忍的既有例外（規則 15 子句、範例檔註解、受測者 ID 佔位） |
| `narrative_cleaner` | 9 | 198 列敘事不符 / 110 列相符 |

**結論：四支紅燈的全部差異 ＝ 02 分頁 `CIA_33_A` 的 K 欄 ＋ 08 分頁敘事本文。結構面（標頭、條數、順序、區塊歸屬、名單區塊、任務指令、System 區塊）全部通過。**

### 8.1 唯一的關鍵動作：重新產生三份 LOG 範例

四支紅燈（`narrative_cleaner`／`interaction_selector`／`log_assembler`／`trait_blocks`）比對的都是同一組東西——`docs/0917/Traitty_調整_20260917/` 的三份 v8 範例，而它們的敘事是 V6.2 產出的。**基準與資料屬於不同版本，這四支就不可能綠。**

所以要做的是把範例換成 V7 產出的版本（v9）。

**誰來產？建議由我方產、客戶簽核。** 理由是組裝邏輯在我方：範例的 `[SYSTEM PROMPT]` 與【輸入數據】區塊完全由打包器生成，`scripts/_gen_coverage_log.py` 就是做這件事的。要求客戶自己產，等於要求他們重建一套打包器。

**流程：**

1. 在一個**暫用資料庫**匯入 V7（不要動 `ai_chatbot_v2`），避免簽核前就改動線上資料。
2. 以三份 v8 範例的相同輸入條件（受測者組合、題目 idx）重新產生三份 LOG。
3. 與 v8 範例做 diff，確認**差異只落在敘事本文**——標頭、區塊順序、條數、任務指令、System 區塊都不該變。§3 的量測已經預告了這一點：`interaction_selector` 的標頭與條數（19/19、49/49）本來就全過。
4. 把三份新範例與 diff 一起交客戶簽核。
5. 簽核後放進 `docs/<日期>/`，把四支腳本的 `PKG`／`EXAMPLES`／`CASES` 改指過去。

**這一步不能跳過，也不能由實作方單方面決定**——範例是 DoD 第 1 條的驗收基準，等於驗收標準本身。

> **必須講清楚的代價：由我方產生範例，會讓這四支從「獨立驗收」退化成「自我比對」。**
>
> `verify_narrative_cleaner` 現在的意義是「我方清洗器的輸出，與客戶獨立產出的範例逐字相同」。若範例改由我方用同一套程式、同一個資料庫產生，這條斷言就變成「我方的輸出等於我方的輸出」——只有在程式不具決定性時才會失敗。其餘三支同理。
>
> 所以第 4 步的簽核**不能只簽 diff**：客戶要實際讀過新範例的敘事內容，確認那就是他們要的文字。獨立性從「獨立產出」轉成「獨立審閱」，這比原本弱，但只要客戶真的讀過就仍然有效。
>
> 若客戶有能力自行產出範例，優先請他們產——那才保得住原本的獨立性。

### 8.2 `verify_calibration` 不需要動作

V7 的 K 欄是「…資訊可信度需交叉驗證」，含「可信度」，而該腳本的判準是
`'佐證' in index_line or '可信度' in index_line`。**匯入 V7 即自動由紅轉綠。**

但要記錄一件語意上的改變：b §4 的「可信度句」原本引導的是「以行為事例佐證」，V7 改成「交叉驗證」後字面仍成立、方向卻不同。這會牽動 §8.3。

### 8.3 必要配套：`EVIDENCE_TERMS` 必須加詞（U5-5 從選配變成必做）

`completeness_check.EVIDENCE_TERMS` 目前是 `('佐證', '行為事例', '工作樣本', '不以單次')`，而 **V7 的 K 欄一個都不含**（V6.2 含「佐證」與「行為事例」）。

資料不再示範那四個詞，卻仍用那四個詞去驗回答——這個組合只會讓 `calibration_evidence` 更容易失敗。所以採用 V7 的話，`EVIDENCE_TERMS` 必須補上 `交叉驗證`、`多方驗證`，並同步 `b §8` 的詞表描述。

> **這不是在修目前 66% 的失敗率。** 那個數字是在 V6.2 資料在線上時量到的（2026-08-18 失敗 13 次、0831 失敗 9 次，當時 payload 裡明明帶著「以行為事例佐證」），成因另有其他，尚未定位。此處只是讓詞表與新資料對齊，避免多疊一個失敗來源。

### 8.4 文件面：四處內容正本要改

### 8.5 基準測試抓不到、但仍然存在的兩件事

「通過測試」不等於「沒有問題」。採用 V7 之後，下列兩項**不會讓任何一支 verify 變紅**，但仍然存在：

### 8.5b 已知的第二條匯入路徑（自檢時發現）

`/api/admin/traits/upload`（`api_v2/admin/trait_importer.py`）是 CLI 之外的第二條匯入路徑。查過之後：

| 守門 | 狀態 |
|---|---|
| 備份（五張表、FK 順序） | **有**，`create_backup_sql()` 與 CLI 同一套 |
| `trait_endpoints` 跨 TRUNCATE 保全 | **有**，`_snapshot_endpoints()` / `_restore_endpoints()` |
| **U0 的 `--spec-version` fallback** | **沒有**——第 150 行仍是 `'version': _cell(row, COL['version'])` |

所以從 admin UI 匯入 V7，`trait_bands.version` 會寫回 NULL，U0「庫內是哪一版變成查得到」的效果就沒了（該欄在歷來每一份 spec 都是空的）。

# 阻斷項：V6.3 的 08 分頁敘事大規模回歸，V7 沿用

日期：2026-09-18
發現時機：執行 P0 取驗收基線時，5 支 verify 腳本未通過，追根因追出來的
狀態：**U4-2（V7 匯入 DB）暫停，等客戶確認**
影響：**已經在線上**——DB 現在就是 V6.3

---

## 1. 一句話

`0915改特質 02_08 V6.3 spec_.xlsx` 把 08 分頁 **2389 列裡的 1053 列（44%）敘事換成了較舊、較短的版本**，平均長度從 181 字掉到 71 字，同時把規範明禁的絕對化措辭大量帶回來。`04_SPEC_0917_V7.xlsx` 原封不動沿用了這個狀態（V6.3→V7 只再動 42 列）。

**照原訂計畫匯入 V7，等於把這個回歸鎖進資料庫。**

## 2. 證據

### 2.1 規模

| 比對 | 清洗後不同的列數 |
|---|---|
| V6.2 → V6.3 | **1053 / 2389（44%）** |
| V6.3 → V7 | 42 |

1053 列裡有 **1007 列變短**，平均長度 **181 字 → 71 字**。

### 2.2 內容形態

| 版本 | `CIA_01_A × CIA_09_A` 的敘事 |
|---|---|
| V6.2 | 表現為「長線自持的推進者」。他對品質與進度的要求一貫，不需要外部催促也能持續把工作往前推；同時面對眼前輕鬆的誘惑，他多半能守住原本的節奏，不會為了一時舒服偏離原本計畫… |
| V6.3 / V7 | 長期目標的長跑者。具備極強的抗誘惑能力與延遲滿足感，能自主完成長期艱難任務。 |

V6.2 是行為導向、帶機率性措辭的寫法；V6.3 是構念式、帶絕對化措辭的舊寫法。

### 2.3 絕對化措辭（全域輸出規範乙-5 明禁）

| 詞 | V6.2 | V6.3 | V7 |
|---|---|---|---|
| 極強 | 4 | **56** | 56 |
| 極度 | 13 | **90** | 90 |
| 絕對 | 2 | **14** | 14 |

規範乙-5 寫的是「一律使用機率性措辭；禁止絕對化」。這些字現在住在**注入給模型的資料裡**，等於一邊叫模型別寫、一邊把範例餵給它。

### 2.4 校準機制連帶失效

b §4 說「校準由資料自帶：索引時行為面向尾句自帶可信度句」。三個校準特質 band A 的敘述：

| 版本 | ANI_23_A / CIA_33_A |
|---|---|
| V6.2 | …不利於己的部分較少主動揭露；**其自述內容的可信度需以行為事例佐證。** |
| V6.3 | 明顯傾向以社會期待方式作答，可能歪曲信念與答案以取得認可，導致評鑑可用性下降。 |
| V7 | 答題或表達時傾向以社會期待的方式呈現，可能修飾說法與答案以取得認可，資訊可信度需交叉驗證。 |

**「以行為事例佐證」這句從 V6.3 起就不在資料裡了。** 而 b §8 的佐證檢查要的正是 `佐證／行為事例／工作樣本／不以單次` 這四個詞。

這就是 `calibration_evidence` 失敗率 66%（50 筆適用、17 過 33 敗）的根因——**不是模型不配合，是資料不再叫它這樣寫**。先前把這一項歸為「V7 可能讓失敗率上升」是錯的：**V6.3 就已經讓它失效，而 DB 現在就是 V6.3**。

## 3. 這解釋了基線為什麼不是綠的

P0 取基線時 31 支跑出 26 過 5 敗。五支全是同一個根因——DB（V6.3）與客戶凍結的範例（V6.2 產出）對不上：

| 腳本 | 症狀 |
|---|---|
| `verify_narrative_cleaner` | 198 列不符 / 110 列相符 |
| `verify_trait_blocks` | CIA_33_A 索引行少了可信度句 |
| `verify_calibration` | 「索引行已自帶可信度句」這條判定失敗 |
| `verify_interaction_selector` | 交互敘事逐字比對不符 |
| `verify_log_assembler` | 範例逐行 0 差異比對不符 |

**這五支不是本次變更造成的，而且匯入 V7 也修不好**——V7 沿用 V6.3 的敘事。

## 4. 最可能的成因（待客戶確認）

V6.3 的檔名是「0915**改特質**」，客戶的意圖是改特質名稱（配合 CSR_23 等改字）。但產出的檔案有 44% 的敘事退回舊版、絕對化措辭暴增、校準句消失——**這比較像是在一份較舊的底稿上套用 0915 的改字，而不是在 V6.2 上改**。

支持這個推測的是：客戶自己最新的 v8 範例（0917 交付）**仍然帶著 V6.2 的敘事文字**。如果 V6.3 的簡略版是有意的改版，範例應該跟著換掉才對。

但這只是推測。**必須由客戶確認哪一版是他們要的**，不能由實作方代為決定——這是內容正本的歸屬問題。

## 5. 要問客戶的問題

> 0915 的「改特質」是否只打算改特質名稱？比對發現 V6.3 相對 V6.2 另外替換了 1053 列（44%）交互敘事，內容退回較舊的簡略版本，平均長度從 181 字降到 71 字，「極強／極度／絕對」等規範禁用的絕對化措辭增加為 7–14 倍，三個校準特質的「以行為事例佐證」句也一併消失。V7 沿用了這個狀態。
>
> 請確認：**(a)** 這是有意的改版，還是在舊底稿上改字造成的？**(b)** 若非本意，請在 V6.2 的敘事基礎上重做一份 V7.2。

## 7. 驗收基線的處置

在客戶回覆前，那 5 支會一直紅。**Gate 的標準改為「不得出現新的失敗」**，而不是「全綠」。基線簽名（2026-09-18，本機，專案 venv）：

```
[verify_all] 通過 26 / 31
未通過：verify_calibration / verify_interaction_selector / verify_log_assembler
        verify_narrative_cleaner / verify_trait_blocks
```

每個單元完成後跑 `python scripts/verify_all.py`，**通過數必須 >= 26，且未通過清單必須是上面這五支的子集**。

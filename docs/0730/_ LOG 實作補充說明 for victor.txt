# LOG 打包器實作補充說明

## 一、作答校準：「零工序」的正確定義

### 1. 規則解釋

「校準零工序」只代表：

- 不新增獨立的 `[作答校準]` 文字區塊。
- 不由程式自行撰寫校準說明。
- 不修改資料正本中的敘事文字。

但程式仍須辨識固定的校準特質：

- `CIA_33`
- `ANI_23`
- `SPA_12`

並在以下三處使用：

1. 交互作用選列。
2. 交互作用子區塊分組。
3. LLM 回答後的佐證措辭檢查。

校準特質若沒有被題目匡列，不得因此升成完整特質區塊；它仍留在「其他特質索引」。

### 2. 匡列型案例

假設：

- 本題匡列集合 `S = {CIA_16, CIA_18}`
- 受測者另有 `CIA_33_A`
- `CIA_33` 是校準特質，但不在本題匡列集合

組裝結果：

- `CIA_16`、`CIA_18`：進入「判讀主體特質」完整區塊。
- `CIA_33_A`：留在「其他特質索引」，不升成完整區塊。
- 不另外生成 `[作答校準]` 區塊。

若正本存在下列交互：

- `CIA_16_A × CIA_33_A`：因為其中一端是本題匡列特質 `CIA_16`，歸入「交互作用——本題相關」。
- `CIA_33_A × CIA_11_B`：若兩端都不在本題匡列集合，但因為含校準特質而被選入，歸入「交互作用——作答校準與風險提示」。

### 3. 回答後檢查案例

若受測者的校準特質為 A 段，回答中至少要出現一種佐證語意，例如：

- 建議搭配實際行為事例確認。
- 可再參考工作樣本或主管觀察。
- 不宜只根據單次自陳結果判斷。

若回答完全沒有這類語意，完整性檢查應回報：

```text
含社會期望反應 A 段，但回答缺少佐證類措辭。
```

### 4. 驗收案例

| 測試情境 | 預期結果 |
|---|---|
| 校準特質未被匡列 | 留在索引區，不升完整區塊 |
| 校準特質被題目匡列 | 依一般匡列規則進入完整區塊 |
| 交互列只因校準特質被選入 | 歸入「作答校準與風險提示」 |
| 交互列同時包含匡列特質與校準特質 | 歸入「本題相關」 |
| 校準特質為 A 段，回答有佐證語意 | 通過 |
| 校準特質為 A 段，回答沒有佐證語意 | 重生一次；仍失敗則轉人工 |
| 輸出中出現獨立 `[作答校準]` meta 區塊 | 驗收失敗 |

## 二、`expected_sections`：輸出段落完整性檢查

### 1. 現有問題

目前每題只有一份 `expected_sections`，但許多題目的單人版與多人版使用不同段落標題。

例如「工作中的主要優勢與潛力」：

單人版預期段落為：

- 自然優勢行為
- 潛在發展方向
- 優勢發揮的情境條件
- 主管使用提醒

多人版指令要求的內容卻是：

- 對象間差異比對
- 協同與互補優勢
- 合作挑戰與拉扯
- 發展與配置策略

若多人回答完全遵照多人版指令，使用單人版 `expected_sections` 檢查仍會被判定缺少四個段落。

因此目前的資料不能直接作為多人版驗收契約。

### 2. 建議資料格式

每題應拆成：

```json
{
  "expected_sections_single": [
    "自然優勢行為",
    "潛在發展方向",
    "優勢發揮的情境條件",
    "主管使用提醒"
  ],
  "expected_sections_multi": [
    "工作優勢與潛力差異比對",
    "協同與互補優勢",
    "合作挑戰與拉扯",
    "發展與配置策略"
  ]
}
```

執行時：

- 一位受測者：使用 `expected_sections_single`
- 多位受測者：使用 `expected_sections_multi`
- 不得在 runtime 從指令文字自行猜測段落

題庫指令也必須要求 LLM 使用與上述欄位完全相同的標題。

### 3. 「子集寬鬆判定」的定義

建議明確定義為：

```text
expected_sections ⊆ 回答實際段落標題
```

也就是：

- 預期段落必須全部存在。
- 回答可以有額外段落。
- 不要求回答只能有這些段落。
- 不可只因預期文字出現在正文中就算通過，必須出現在段落標題。
- 可忽略標題前的數字、空白及全形／半形冒號。

例如預期標題為「主管使用提醒」：

| 回答內容 | 結果 |
|---|---|
| `4. 主管使用提醒` | 通過 |
| `四、主管使用提醒：` | 通過 |
| 正文寫著「以下提供主管使用提醒」 | 不通過，因為不是段落標題 |
| `主管注意事項` | 不通過，名稱不同；應先由內容方統一用語 |

### 4. 建議失敗政策

段落缺漏與內部資料洩漏應分開處理：

#### 段落缺漏：軟性檢查

1. 第一次缺漏：把缺少的段落名稱交給 LLM，重生一次。
2. 第二次仍缺漏：狀態改成 `manual_review`，不自動放行。
3. 不應讓服務崩潰，也不應與洩漏重試共用次數。

#### 內部標記洩漏：硬性檢查

若回答含特質 ID、band、內部標籤等：

1. 必須重寫或遮罩後重送。
2. 最終仍有洩漏時不得回傳前端。
3. 狀態改成 `blocked` 或 `manual_review`。

#### 空陣列

若該題沒有固定段落：

```json
{
  "expected_sections_single": [],
  "expected_sections_note": "本題未定義固定段落標題"
}
```

程式應：

- 略過段落檢查。
- 寫入 audit log。
- 不得顯示成「段落檢查已通過」。

建議紀錄：

```text
本題未做段落齊全檢查；原因：指令未定義固定段落標題。
```

### 5. 驗收案例

| 測試情境 | 預期結果 |
|---|---|
| 單人題使用完整單人標題 | 通過 |
| 多人題使用完整多人標題 | 通過 |
| 多人回答正確，但拿單人清單檢查 | 測試設計錯誤，不得發生 |
| 缺一個必要標題 | 重生一次 |
| 重生後仍缺標題 | `manual_review` |
| 預期標題只出現在正文 | 不通過 |
| 有全部預期標題，另有額外段落 | 通過 |
| `expected_sections` 為空 | 略過並留下 log |

## 三、everyday 詞：條件式放行規則

### 1. 規則解釋

everyday 詞不是「無條件白名單」，而是「日常使用時放行、構念判定時攔截」。

資料必須從下列巢狀路徑取得：

```text
trait_names_blocklist.everyday_words
band_labels_blocklist.everyday_labels
```

不可從 JSON 頂層讀取。

掃描時還必須遵守 per-request 原則：

- 只掃描本次 payload 實際出現過的特質名稱與標籤。
- 沒有注入本次 payload 的名稱，不應造成誤報。

### 2. 判定原則

#### 日常語用：放行

詞彙被當成一般中文使用，沒有描述測驗分數、程度或分類。

例如：

- 面對挑戰時展現韌性。
- 建立彼此的信任。
- 他願意表達感謝。
- 團隊需要快速轉換做法。
- 高壓下的情緒反應可能比較明顯。

#### 構念式用法：攔截

詞彙被用來表達測驗結果、程度、分數、區間或高低判定。

例如：

- 他的韌性偏高。
- 信任程度偏低。
- 自律性分數很高。
- 他的快速轉換傾向明顯。
- 同理心指標落在高區間。
- 情緒反應較強。

### 3. 目前 regex 需要補強

現有規則可以攔截：

```text
韌性偏高
快速轉換傾向
```

但可能漏掉：

```text
韌性很高
韌性較高
信任度低
情緒反應相對較強
```

這些仍屬於程度或高低判定，應納入攔截測試。

### 4. 非 everyday 詞

如果某個內部特質名稱不在 everyday 清單，例如：

- 心理特權
- 社會期望反應
- 目標效能感

只要在對外回答中直接出現，就應攔截，不需要再判斷是否後接「高／低／程度」。

### 5. 驗收案例

| 回答句子 | 預期 |
|---|---|
| 面對挑戰時展現韌性 | 放行 |
| 韌性偏高 | 攔截 |
| 韌性很高 | 攔截 |
| 建立團隊信任 | 放行 |
| 信任程度偏低 | 攔截 |
| 快速轉換做法 | 放行 |
| 快速轉換傾向明顯 | 攔截 |
| 情緒反應可能較明顯 | 放行；一般情境描述 |
| 情緒反應分數較高 | 攔截 |
| 心理特權 | 直接攔截 |
| 本次未注入「快速轉換」，回答自然使用該詞 | 不應因標籤表而攔截 |

## 四、端到端輸入／輸出範例

### 1. 輸入範例

在 `module_id` 對照表完成前，內部 `question_id` 暫以題庫 `idx` 為準：

```json
{
  "respondents": [
    {
      "name": "王小明",
      "id": "R001",
      "tests": ["CIA"],
      "scores": {
        "CIA_05": "B",
        "CIA_16": "A",
        "CIA_18": "A",
        "CIA_33": "A"
      }
    }
  ],
  "mode": "quick",
  "question_id": 5
}
```

### 2. 處理流程

```text
驗證人數與 audience
→ 依 question_id 取得題目
→ 取得匡列集合 S
→ 組特質完整區塊與索引區
→ 選取並分組交互作用
→ 加入 System Prompt 與任務指令
→ 呼叫 LLM
→ 執行洩漏掃描
→ 執行 expected_sections／校準佐證檢查
→ 放行、重生、阻擋或轉人工
```

### 3. 內部回傳範例

```json
{
  "answer": "LLM 最終回答",
  "status": "ok",
  "audit": {
    "question_id": 5,
    "audience": "single",
    "expected_sections_check": "passed",
    "calibration_evidence_check": "passed",
    "leakage_hits": [],
    "retry_count": {
      "leakage": 0,
      "completeness": 0
    }
  }
}
```

可能狀態：

- `ok`：全部檢查通過。
- `manual_review`：段落或佐證重生一次後仍不完整。
- `blocked`：仍有內部資料洩漏，不得回傳前端。

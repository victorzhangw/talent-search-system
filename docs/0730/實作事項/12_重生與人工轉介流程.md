# 12. 出口掃描／完整性檢查失敗後的重生與人工轉介流程

**類型**：核心邏輯｜**優先度**：P1｜**依賴**：09（出口掃描器）、10（完整性檢查）

## 目標

把事項 09（出口掃描）與事項 10（完整性檢查）串成一個完整的「呼叫 LLM → 檢查 → 不過則重生 → 仍不過則轉狀態」流程，並確保兩種失敗原因的重試次數**分開計數**、最終狀態機正確。

## 為什麼要獨立於 09/10 之外再列一項

09 和 10 各自定義了「自己不過時要重生」，但兩者合起來跑時有兩個容易做錯的地方：(1) 兩種重試次數如果共用同一個計數器，會出現「因為洩漏重試用完了額度，導致段落缺漏就沒機會重生」這種耦合失真；(2) 最終狀態要能區分「洩漏未清乾淨（禁止回傳）」與「段落缺漏但無洩漏（人工復核即可，內容本身沒有洩漏風險）」——兩者的嚴重程度不同，不該用同一個 `manual_review` 蓋掉差異，至少 audit log 要能區分。

## 規則來源（分散在 b§7、b§8，此處整合）

`b_打包規則_v2_20260727.md` §7：
> 命中＝重寫或遮罩後重送，**直到掃描乾淨才可放行**；洩漏重試與 §8 段落缺漏的 1 次重生**分開計數**。若最終仍有洩漏，**不得把該回覆回傳前端**（阻擋並落人工）。

§8：
> 不過 → 帶「缺了什麼」的具體原因重生成一次（上限 1 次，再不過落人工）。

## 需要跟客戶/內容方確認的疑點（不是我方能單方決定的細節）

`b_打包規則_v2_20260727.md` §7 對洩漏重試寫的是「直到掃描乾淨才可放行」，**沒有明講重試次數上限**；但 `00_外包交接說明.md` DoD 第 4 條與 §14（見事項 14）講的是「紅隊實測內部標記殘留 0 才放行」，這是**驗收標準**而非 runtime 重試次數規格。若 runtime 真的「無限重試直到乾淨」，理論上存在 LLM 持續產生洩漏、迴圈不收斂的風險（雖然實務機率低，但仍是需要工程上兜底的情境）。

**建議**：runtime 對洩漏重試也設一個實務上限（例如 2–3 次），超過上限則轉 `manual_review`／`blocked`，不做真正的無限迴圈；同時把這個上限值列為「回問內容方確認是否可接受」的項目（依 `00_外包交接說明.md` 的升級路徑：打包程序歧義先對照 b 文件，仍不明回內容方）。此建議已記錄於事項 15。

## 狀態機（逐字引用 `_ LOG 實作補充說明 for victor.txt` 第 366–370 行）

可能狀態：
- `ok`：全部檢查通過。
- `manual_review`：段落或佐證重生一次後仍不完整。
- `blocked`：仍有內部資料洩漏，不得回傳前端。

## 內部回傳範例（逐字引用，第 346–364 行）

```json
{
  "answer": "LLM 最終回答",
  "status": "ok",
  "audit": {
    "question_id": 5,
    "audience": "single",
    "expected_sections_check": "passed",
    "calibration_evidence_check": "passed",
    "leakage_hits": [],
    "retry_count": {
      "leakage": 0,
      "completeness": 0
    }
  }
}
```

## 可直接沿用（但需強化）的參考實作

`02_參考程式碼_打包器骨架.py` 第 395–404 行 `run_with_exit_guard()`：
```python
def run_with_exit_guard(log_text, scan, respondents, question, store):
    answer = call_llm(log_text)
    hits = scan(answer); miss = completeness_check(answer, respondents, question, store)
    if hits or miss:
        reason = f"（重生原因：洩漏={hits}；缺漏={miss}）"
        answer = call_llm(log_text + "\n\n[重生要求] " + reason)
        hits = scan(answer); miss = completeness_check(answer, respondents, question, store)
        if hits or miss:
            return answer, {"status": "manual_review", "hits": hits, "miss": miss}
    return answer, {"status": "ok"}
```

**這個骨架版本把洩漏（hits）與完整性（miss）兩種失敗合併成同一次重試、同一個計數器**，與 §7「洩漏重試與 §8 完整性重試分開計數」的規格文字不完全一致；且骨架版本的最終失敗狀態一律是 `manual_review`，沒有依規格區分「仍有洩漏 → `blocked`，不得回傳」與「只是段落缺漏 → `manual_review`」。**本事項要把骨架的合併版本，改寫成規格要求的分離計數＋分離終態版本**，並補上事項的 audit 欄位格式（`retry_count.leakage` / `retry_count.completeness` 分開）。

## 驗收標準

- [ ] 洩漏與完整性重試次數各自獨立計數，不互相扣抵。
- [ ] 最終仍有洩漏 → 狀態為 `blocked`，`answer` 絕不回傳給前端呼叫方。
- [ ] 最終只是段落/佐證缺漏（無洩漏）→ 狀態為 `manual_review`，可考慮回傳（依你的產品決策：是否要把 `manual_review` 的內容先擋住等人工看過，或先回傳給使用者、事後補審——這點規格文件未明講，需要你或內容方裁定，見事項 15）。
- [ ] audit 物件格式與上方 JSON 範例欄位一致（`expected_sections_check`／`calibration_evidence_check`／`leakage_hits`／`retry_count`）。
- [ ] 重生請求時附帶「缺了什麼」的具體原因（不是泛用的「請重新回答」）。

## 補充核對（2026-07-31 複查）：結構化 audit 紀錄目前完全不存在，且串流架構會卡住整個「檢查後才放行」的前提

### 1. 結構化 audit log——現有 log 只記錄「送出前」，沒有任何機制記錄「檢查後」的結果

現有 repo 有三種 log：`prompts.log`（`rag_engine.py._log_prompt()`，只記錄送出前的 system prompt + user query）、`rag_service.log`（一般除錯 log）、`trait_match_audit.log`（`context_builder.py` 的 `trait_match_audit_logger`，記錄特質比對失敗原因，跟本事項無關）。**這三個都不是本事項需要的東西**——b§8 明文要求「不得無聲通過」的 log，以及上方 JSON 範例的 `audit` 物件（`expected_sections_check`／`calibration_evidence_check`／`leakage_hits`／`retry_count`），是**每次請求執行完事項 09/10 檢查、跑完重生流程後，最終產出的一筆結構化紀錄**，性質上更接近「稽核用的請求級交易紀錄」，不是給人肉眼讀的除錯訊息。

**建議**：另開一個獨立的結構化 log 出口（例如寫進 DB 一張新表，或至少是 JSON-lines 格式的獨立 log 檔，不與 `prompts.log` 混在一起），每次請求跑完本事項的流程後寫入一筆，欄位對齊上方 JSON 範例。這張紀錄的價值在於「日後被問到『這通對話為什麼卡住/為什麼轉人工』時查得到」，跟現有三種 log 的除錯用途不同，不要合併著寫。

### 2. 串流架構衝突——這是本事項能不能真正落地的前提，需要你先拍板

`BackEnd/api_v2/routes/chat.py` 第 420–433 行，目前 LLM 回答是**逐 token 即時透過 SSE 串流給前端**（`for chunk in response_stream: ... yield token`），使用者一邊看 LLM 一邊在後端生成的內容，是「打字機」體驗。

但本事項的核心規則是「命中＝重寫或遮罩後重送，直到掃描乾淨才可放行」「若最終仍有洩漏，不得回傳前端」——**這個前提要求先拿到完整回答、掃描通過後才能送出**，跟現行「邊生成邊送」的串流方式直接衝突：等你掃描完一整段回答有沒有洩漏時，前面的 token 早就已經送到使用者瀏覽器上了，即使判定要 `blocked`，也已經來不及擋。

這不是本事項可以自己決定繞過的細節，是一個**架構層的取捨**，需要你先決定要哪種做法，因為會影響 `chat.py` 的串流邏輯要不要大改。詳細討論另立一份文件，見 [16_串流架構與輸出攔截衝突](16_串流架構與輸出攔截衝突.md)——本事項（12）的重生／狀態機邏輯本身照樣可以先實作，但「最終狀態要能在使用者看到內容前生效」這件事，要等 16 的架構決策定案後才能真正掛上線。

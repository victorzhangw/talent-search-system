# 07. LOG 組裝與輸出格式（b§5）＋ audience 前置驗證

**類型**：核心邏輯｜**優先度**：P1｜**依賴**：01（System文本）、05（特質分流）、06（交互選列）

## 目標

把事項 01/05/06 的產出，依固定順序組裝成最終 LOG payload 字串；支援單人與多人（每人一個 `### 區塊`）；組裝前先做 `audience` 驗證，人數不符即拒絕請求。

## 組裝順序（逐字引用 `b_打包規則_v2_20260727.md` §5）

```
[SYSTEM PROMPT]（a 文件第一部分，靜態常數）
---
## 【輸入數據】
### [受測者 | 姓名 | ID]          ←（網站基本欄位為保留擴充位，目前不輸出）
#### 判讀主體特質                    ←匡列型用此字串
#### 判讀主體特質（全人型＝全部特質）  ←全人型用此字串
#### 其他特質索引（僅供關聯參考，非本題判讀主體）
#### 交互作用——本題相關（匡列型）
#### 交互作用——作答校準與風險提示
#### 交互作用——其他參考（全人型）
---
[任務指令]（題庫表該題清理後指令；多人題用多人欄）
```

多人情境：每位受測者一組「###受測者＋區塊」，依序排列；任務指令用多人欄版本。實例見 `新版LOG範例_多人型_會議團隊_v7.txt`（2 位受測者，各一個 `### [受測者]` 區塊）。

## 受測者標頭格式（逐字引用）

```
### [受測者 | 王智弘 | RESP_XXXX]
（網站端基本欄位可續掛於此）
```
> 舊版人名後的空括號 `()` 已移除，這是版式說明文件特別提醒的既往缺陷，不要重新引入。

## audience 前置驗證（拒絕請求，不可續組）

`b_打包規則_v2_20260727.md` §1.1：
> **audience 前置驗證（組裝前必做，不符即拒絕請求）**：題庫表每題有 `audience`＝`single_only`／`multi_only`／`both`。人數與之不符必須**拒絕請求**，不可繼續組裝——`single_only` 題的 `instruction_multi` 是佔位字串「僅適用單人」（反之亦然），照組會送出只有 5 個字的壞任務指令。

參考實作（`02_參考程式碼_打包器骨架.py` 第 246–255 行 `check_audience()`）已給出完整判斷邏輯，可直接沿用：人數>1 但 `audience=="single_only"` → 拋錯；人數=1 但 `audience=="multi_only"` → 拋錯。

## 任務指令組裝

- 題庫題：`question["instruction_multi"]`（多人）或 `question["instruction_single"]`（單人）。
- 自由提問：`[任務指令]` 直接是使用者原始提問文字（`mode=free` 時 `user_query` 必填）。

## 輸入 schema（逐字引用 `b_打包規則_v2_20260727.md` §1.1）

```
{
  respondent: { name: str, id: str, tests: [ "ANI"|"CIA"|"SPA"|"CSR" ], scores: { trait_id: "A"|"B"|"C" } },
  mode: "quick" | "free",
  question_id: str,        // mode=quick 時必填，對應題庫表
  user_query: str          // mode=free 時必填，使用者原始提問
}
多人情境：respondents: [ {…}, … ]，逐人一組 ### 區塊；任務指令用多人欄。
```

## 補充核對（2026-07-31 複查）：既有架構把 LOG 拆成兩則訊息、任務指令沒有獨立欄位、且每題各自帶了一份重複的禁令文字

### 1. LOG 目前不是「一份文字」，是拆成 system/user 兩則訊息送出

客戶參考骨架（`assemble_log()`）把 `[SYSTEM PROMPT]` + `【輸入數據】` + `[任務指令]` 組成**同一條字串**再整份送 LLM。但現有 `rag_engine.py._call_llm()`（第 521–525 行）送出的是：
```python
messages = [
    {"role": "system", "content": sys_prompt.strip()},
    *history_messages,
    {"role": "user", "content": query}
]
```
`sys_prompt` 是組好的模板（含資料），`query` 是使用者在聊天框打的文字。**這代表現有架構沒有客戶規格裡「任務指令＝題庫表固定文字」這個獨立語意欄位**——快速提問模組路由（`_route_by_module`，第 110–139 行）目前完全没有讀題庫表的 `instruction_single`／`instruction_multi`，任務描述其實是寫死在每個模組各自的 prompt 檔案裡（見下），使用者打的字只是被當成普通 user turn 送進去，跟「任務指令」是兩件事。

本事項要決定：是否比照客戶設計改成「LOG 全文（含任務指令）整份放進 system message，user message 只留使用者真正要問的補充問題（或留空/固定短句）」，還是維持現行「任務指令」用另一種方式融入 system prompt。這是一個需要先拍板的組裝策略，會連動事項 04（`module_id` 對照表要不要順便帶出 `instruction_*` 文字）。

### 2. 每個既有模組 prompt 檔案都各自帶了一份重複的禁令文字——這正是客戶新規格要統一取代的對象

實際打開 `BackEnd/api_v2/prompts/modules/mgmt_pressure_single.txt` 可以看到，現有的每個模組 prompt 檔案結構其實跟客戶的 LOG 三段式很像：先是任務說明＋輸出結構（對應 `[任務指令]`），中間 `---` 分隔，然後 `## 【輸入數據】` 段落放 `{base_analysis}`／`{interactions}`（對應資料層），最後還有一段**該模組自己寫的**「輸出安全防護」清單（例如列出「完美主義、創新力、韌性…」等特質名稱要求勿外洩）。

**這正是 `a_LOG完成版模板_v2_20260727.md` 開頭講的「取代各題原本重複的禁止段與判讀規範段」要解決的問題**：現在 22 個模組各自維護一份長得很像但不保證一致的黑名單／禁令文字，改一條規則要改 22 個檔案；客戶的新設計是把這些通則全部收斂成 a 文件的 20 條全域規範，題目層只留「題意說明＋輸出段落架構」。本事項的一部分工作，就是把這 22 個現存 prompt 檔案裡的「禁令段」抽掉，換成統一的 System 全文（事項 01 的 `load_system_prompt()`），只保留每個模組真正獨有的「題意說明＋輸出段落架構」那一段。

### 3. Log／稽核紀錄的兩個新增缺口（回應你的提問）

- **既有 `_log_prompt()`（`rag_engine.py` 第 484–497 行）只記錄送出前的內容**，寫進 `prompts.log`：`[SYSTEM PROMPT]\n{sys_prompt}\n\n[USER QUERY]\n{user_query}`。等 LOG 組裝格式改成新規格的三段式結構後，這裡記錄的內容格式要同步更新，否則 `prompts.log` 裡存的內容跟實際送出的 LOG 對不上。
- **`b_打包規則_v2_20260727.md` §8 要求的結構化稽核紀錄，目前完全不存在**：「程式須...必須 log『本題未做段落齊全檢查（原因：...）』——不得無聲通過」，以及 `_ LOG 實作補充說明 for victor.txt` 給的內部回傳範例裡那個 `audit` 物件（`expected_sections_check`／`calibration_evidence_check`／`leakage_hits`／`retry_count`）——這是**每次請求都要產出的結構化紀錄**，跟現有的自由文字 `prompts.log`／`rag_service.log` 性質不同，用途是事後稽核「這次為什麼放行/為什麼轉人工」。這個結構化 audit 紀錄的實際寫入點在事項 09（掃描結果）與事項 10（完整性檢查結果）跑完之後，最終彙整落地在事項 12（見該文件補充章節）。本事項組裝 LOG 時，需要預留這個 audit 結構會用到的欄位（例如 `question_id`／`audience`），供後面串起來。

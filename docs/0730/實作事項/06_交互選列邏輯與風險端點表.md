# 06. 交互選列邏輯（匡列型／全人型，b§3）＋ 風險端點表掛載

**類型**：核心邏輯｜**優先度**：P1｜**依賴**：02（交互正本）、05（特質分流）

## 目標

從候選交互列（兩端都在受測者特質集合 P 內）中，依匡列型／全人型兩種模式分別分組成子區塊；掛載 71 條風險端點表，命中時保證該交互被納入。

## 統一原則（`b_打包規則_v2_20260727.md` §3，逐字）

> **相關的全注入、不做任意砍量、無條數上限**。候選：08 分頁中「配對兩端 (ID, band) 都 ∈ P」的列；鏡像去重（同一無序配對取列序在前者）；敘事開頭「與 XXX_nn (名) Y聯動：」依 T5 剝除（已在事項 02 處理）。

> **不設任何條數上限或體積防呆（用戶裁定）**：候選池天生有限（無跨測驗交互，雙測驗約 136、四測驗上限約 300–450），不會爆炸。舊版「覆蓋＋補充10＋>90 截斷」為砍量設計，已作廢——它讓全人模式反而比匡列模式不完整（本末倒置），故移除。**若你在任何舊版文件或口頭需求中看到 25/40 條上限、覆蓋輪、補充輪等字眼，那些已被推翻，不要實作。**

## 匡列型（兩步）

```
1. 題意過濾：至少一端 ∈ (S ∪ 校準 ∪ R)（濾掉兩端都與本題無關的配對）
2. 過濾後全部注入，依列序，分兩個子區塊：
   「交互作用——本題相關」：至少一端 ∈ S 的列
   「交互作用——作答校準與風險提示」：僅因 校準/R 入選的列
```

## 全人型／自由提問（兩步，全注入）

```
1. 不做題意過濾（S＝全部特質，所有候選都相關）。
2. 候選全部注入，依列序，分兩個子區塊：
   「交互作用——作答校準與風險提示」：觸及 (校準 ∪ R) 的列（排前，讀的顯著性高）
   「交互作用——其他參考」：其餘全部
（全人型不出現「本題相關」子區塊）
```

## 輸出格式（逐字引用）

交互塊格式（`a_LOG完成版模板_v2_20260727.md` §2.2）：
```
[交互 | CSR_01_A × CSR_24_C | 卓越進取 × 自我優先]
（敘事本文；開頭「與 XXX_nn (名) Y聯動：」由匯出程式依 regex_pack 確定性剝除，配對資訊已上移標頭）
```

尾註規則（`b_打包規則_v2_20260727.md` §3 註記，程式自動加）：
- 匡列型「本題相關」子區塊 **1–4 條** → 尾註「本題相關交互較少，判讀以特質區塊為主」；**0 條時該子區塊整段不輸出**（不加尾註）。
- 全人型全注入，**無「未注入」尾註、無截斷**。

## 資料欄位對應（2026-07-31 第二次複查）：這裡才是 `injection_set` 的正確用途

事項 05 警告過 `injection_set` 不可拿來當全塊區來源；但**在本事項它是對的欄位**。題庫表的 `injection_note` 寫明：

> 交互過濾集合＝本清單（`injection_set`） ∪ 受測者命中之風險端點特質（見 `risk_endpoints.adopted`）

換句話說，匡列型第 1 步的題意過濾條件「至少一端 ∈ (S ∪ 校準 ∪ R)」，可以直接寫成「至少一端 ∈ (`injection_set` ∪ R)」——實測確認 `injection_set` 對 22 題全數恰好等於 `scoped_traits ∪ {CIA_33, ANI_23, SPA_12}`，兩種寫法等價。客戶參考骨架用的是前者（`trigger = S | store.calibration | R`，第 162 行），也正確；兩種寫法擇一即可，但**不要把兩個欄位的用途搞混**：`injection_set` 用於交互過濾（本事項），`scoped_traits` 用於全塊分流（事項 05）。

## 補充核對（2026-07-31 複查）：既有邏輯只做了單向查詢，且沒有風險端點／校準概念

`context_builder.py` 第 223–245 行目前的交互選列邏輯是：對受測者每個已處理特質，查 `TraitInteraction.primary_trait_id == trait_id`（單向，只從「這個特質當 primary」的方向查），再確認 `trigger_trait_id` 的 band 是否吻合，符合就直接全部塞進同一個 `interactions` 字串，**沒有子區塊分組、沒有鏡像去重、沒有風險端點表、沒有校準特質**。

這裡有一個值得注意的技術細節：客戶規格定義候選集是「配對兩端 (ID, band) 都 ∈ P」（**對稱**，不分誰是 primary），且需要「鏡像去重（同一無序配對取列序在前者）」——這暗示 08 正本裡同一組配對可能兩個方向都各存一列（A×B 一列、B×A 一列）。但現有 DB 查詢只用 `primary_trait_id` 單向查，如果 `trait_interactions` 表裡確實兩個方向都有資料列，現有邏輯只會撈到「以該特質為 primary」那一半，另一半（該特質是 trigger 端但另一特質未被當前迴圈處理到）不會出現。**本事項需要先確認 `trait_interactions` 表的資料是單向存（每組配對只存一列）還是雙向存（鏡像存兩列）**，這會決定候選查詢要不要改成對稱查詢（`primary_trait_id IN P OR trigger_trait_id IN P`，兩端都要在 P 內）。

風險端點表（71 條）與校準特質集合（`{CIA_33, ANI_23, SPA_12}`），目前 DB schema 完全沒有對應欄位或表——`TraitBand`／`TraitInteraction` 都沒有 `is_risk_endpoint`／`is_calibration` 這類旗標。實作上不一定需要改 schema：可以比照客戶交付的 `question_injection_table_v9.json` 做法，把 71 端點與 3 個校準 ID 存成**靜態設定檔（JSON 或 Python 常數）**，程式啟動時載入比對，不必動資料庫結構——這是本事項可以自行決定的實作細節，不影響外部行為。

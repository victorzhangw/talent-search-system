# 08. 交付前單元檢查（b§6，四項，每次組裝都跑）

**類型**：品質關卡｜**優先度**：P1｜**依賴**：07（LOG 組裝）

## 目標

每次組裝完 LOG 之後（送 LLM 之前），跑四項確定性檢查，任何一項不過即視為組裝錯誤（不是 LLM 回答問題，是打包程式自己的 bug），需在部署前攔下。

## 四項檢查（逐字引用 `b_打包規則_v2_20260727.md` §6）

```
1. 全塊數 ＝ S∩P 特質數；索引行數 ＝ |P| - 全塊數。
2. 每個交互標頭的兩端 ID 都出現在全塊區或索引區。
3. 全文無 ['、無空括號 ()；殘留括號代號檢查僅適用敘事本文欄，必須排除標頭——標頭的 XXX_nn ID 是合法內部標記且必須保留（見 00 DoD 5、regex_pack 的 strip_trait_id_refs note）。對全文套 T5 會命中上百個合法標頭 ID，導致檢查必然失敗或誤剝 ID。
4. 子區塊歸屬正確：本題相關列至少一端 ∈ S。
```

## 關鍵陷阱（明確標注，避免誤實作）

第 3 項是全案文件中反覆強調的一個坑：`LOG檔版式區塊說明_v2_20260728.docx` 特別寫了一段警告：
> v1.2 寫「跑 regex_pack 全部規則掃全文」是錯的：實測對全人型範例全文套用會命中 207 次，全是合法標頭 ID。照做會導致檢查必然失敗，或為了通過而剝掉標頭 ID、破壞 runtime 消歧。

換句話說：**第 3 項檢查只能查字面符號（`['`、`()`、`（）`），不能對全文重新跑一次 regex_pack 的剝除規則**——regex_pack 只在事項 02 讀取交互敘事時套用過一次，此處不可重跑。

## 可直接沿用的參考實作

`02_參考程式碼_打包器骨架.py` 第 278–303 行 `unit_check()`，已完整實作四項邏輯，回傳問題清單（空清單＝全過）。可直接改寫進本 repo，把 `au`（audit dict）換成事項 05/06 產出的實際資料結構。

## 這一項檢查失敗時該怎麼處理

`unit_check()` 失敗代表**打包程式本身有 bug**（不是使用者輸入問題，也不是 LLM 品質問題）——這種情況不該重試、不該讓步，而是要讓組裝直接失敗並記錄，因為它意味著資料層或分流/選列邏輯（事項 01/02/05/06）某處有錯。建議：檢查失敗時拋例外中止本次請求，記錄完整 audit 內容供除錯，不要把有問題的 LOG 送給 LLM。

## 驗收標準

- [ ] 四項檢查各自獨立可測（可故意構造壞資料觸發每一項失敗，確認檢查邏輯真的能抓到）。
- [ ] 用兩份範例檔的真實受測者資料重跑組裝，四項檢查全數通過。
- [ ] 第 3 項檢查不會對合法的 `XXX_nn` 標頭 ID 誤判——用全人型範例（`新版LOG範例_全人型_雙測驗_v7.txt`，特質量大、標頭密集）驗證零誤報。
- [ ] 檢查失敗時，錯誤訊息含足夠資訊定位問題（哪位受測者、哪個特質/交互、違反哪一項）。

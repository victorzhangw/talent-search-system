# 15. 外部依賴與待回覆清單（非我方可獨立完成）

**類型**：阻斷追蹤｜**優先度**：追蹤用，非「做完即結案」的實作項

## 目標

彙整所有需要內容方（Traitty 團隊）或 API 方回覆／配合才能繼續的事項，避免它們散落在各個實作事項文件中被忽略。這份清單本身不是實作任務，是給你（或你轉交給對方）追蹤用的。

## 清單

### 1. API `band` 值域未實測

`03_API對接說明_TalentChatV2.md` §5：schema 只標 `string`，我方系統吃 `A`/`B`/`C`。需要用一次 MOCK 呼叫確認 API 回的是否同碼；若為數字或其他碼，事項 03 的 adapter 要加轉換（分數→band 的切點以我方定義為準）。
**誰處理**：外包（實測）＋ API 方（需憑證，需要對方協助或提供測試帳號）。
**影響事項**：03。

### 2. `module_id ↔ 題目` 對照表未建（2026-07-31 複查後：只需覆核，不需重新設計）

見事項 04 全文。複查發現既有 `quick_modules.json`（22 模組）與題庫表（22 題）依 `idx` 順序逐一比對，分類、順序、`audience`／`candidate_mode` **100% 吻合、0 筆衝突**——這代表對應關係大機率早就存在，只是沒有顯式寫下來（目前靠兩份清單「剛好同順序」這個隱性巧合對齊，沒有明確欄位）。
**誰處理**：內容方**覆核**（確認這個既有位置對應正確、無例外），我方負責把它顯式化成欄位或對照表。
**影響事項**：04（原本判斷是阻斷，現在只需要一次覆核即可解除，不必等待重新設計）。

### 3. 正本 SPA 53 列 `ai_do`／`ai_dont` 缺欄名前綴

`README_最終交付.md`「交付前未結項」第 3 條：正本 SPA 53 列缺「可用於：」「禁止：」前綴（ANI/CIA/CSR 全含，SPA 僅 1/54 自帶）。**程式端已用正規化補上**（見事項 01 的 `_prefix()`），這不阻斷開發，但**資料面根治仍建議修正正本**，減少長期依賴程式層補丁的脆弱性。
**誰處理**：內容方（修正 xlsx 正本）。
**影響事項**：01（目前已有 workaround，非阻斷）。

### 4. 紅隊實測未跑（內部標記殘留 0 的放行標準）

`README_最終交付.md`「交付前未結項」第 4 條，即事項 14 本身——列在這裡是因為它同時也是「外包（我方）需要執行，但需要 LLM 呼叫預算與時間排程」的項目，性質上偏向排程/資源依賴而非邏輯依賴。
**誰處理**：外包（我方），需要事先確認 LLM 呼叫預算來源。
**影響事項**：14。

### 5. `expected_sections` 的 single/multi 拆分（語意工作，非程式邏輯）

見事項 13。JSON 資料本身的拆分需要逐題核對單人/多人指令的實際段落標題，屬於語意判斷，依「零語意邏輯」職責邊界不該由打包程式端自行猜測。
**誰處理**：內容方。
**影響事項**：13、10（在拆分完成前，10 只能用舊的單一 `expected_sections`，多人題的完整性檢查準確度會打折）。

### 6. 洩漏重試次數上限未定案

見事項 12「需要跟客戶/內容方確認的疑點」小節。`b§7` 只寫「直到掃描乾淨才可放行」，未明講 runtime 重試次數上限；建議設一個實務上限（例如 2–3 次）但這是本方建議，非規格明文，應回問內容方是否可接受，或是否有其他期望的 fallback 行為。
**誰處理**：內容方（確認）＋我方（依回覆調整事項 12 的實作）。
**影響事項**：12。

### 7. `manual_review` 狀態的回傳行為未定案

見事項 12。段落/佐證缺漏但無洩漏的 `manual_review` 情境，規格沒有明講此時是否可以先把內容回傳給使用者（同時排入人工複核），還是必須完全擋住直到人工複核完成才能給使用者看。這是產品層決策，不是技術問題。
**誰處理**：你或內容方裁定。
**影響事項**：12。

### 9. band 值域來源：沿用既有的「自己用 score 重算」還是改成「直接信任 API 的 band」（2026-07-31 複查新增）

見事項 03 補充核對。現有 `context_builder.py` 目前是拿 `score` 去查我方 `TraitBand` 表自己算 band，完全沒用 API／前端傳來的 `band` 欄位；客戶規格假設「band 已由伺服器算好，直接用」。兩者是不同的架構選擇，牽動事項 03 的 adapter 要怎麼寫，也連動待回覆項 1（band 值域是否已與我方定義一致）。
**誰處理**：你裁定（產品/架構決策），若選擇改用 API band，需併同待回覆項 1 一起向 API 方確認值域。
**影響事項**：03。

### 10. 出口掃描「未通過不得回傳前端」在現行串流架構下做不到，需要先選一個方案（2026-07-31 複查新增）

見新增事項 16 全文。現行 `chat.py` 是逐 token 即時串流給前端，出口掃描卻需要完整回答才能判斷——兩者衝突，規格文字「不得回傳前端」在不改動串流方式的前提下無法完全落實。事項 16 列了三個選項（完全緩衝／背景掃描事後補救／僅題庫題緩衝），需要你（可能需要一併徵詢產品/前端owner）做選擇。
**誰處理**：你裁定（產品層決策，非純技術問題）。
**影響事項**：09、12、16，以及 `chat.py` 本身。

### 11. 結構化 audit 紀錄要存在哪裡（2026-07-31 複查新增）

見事項 07、12 補充核對。b§8 與內部回傳範例要求的 `audit` 物件，現有三種既有 log（`prompts.log`／`rag_service.log`／`trait_match_audit.log`）都不是為這個用途設計的，性質上更接近「請求級稽核紀錄」。存成 DB 表還是獨立結構化 log 檔，會影響日後查詢/保留政策，建議先確認公司內部對這類稽核資料有沒有既定規範（保留期限、存取權限等），非純技術決定。
**誰處理**：你裁定，必要時徵詢內部資安/合規要求。
**影響事項**：07、12。

### 8. 舊 CIA/SPA 短格式升級（已定案暫緩，僅供留意）

`01_設計總說明與決策定案_v2_20260728.md` §3：決策 #3「舊 CIA/SPA 短格式升級」維持暫緩（backlog），先靠輸出防線（事項 09 出口掃描）壓住。**這不是待回覆項，是已經定案的延後決定**，列在此處只是提醒：若日後有人重提這個需求，先確認是否仍是 backlog 狀態，不要在本次交付範圍內順手做。
**誰處理**：不適用（已定案延後）。

## 建議使用方式

在你決定要實施哪些事項（01–14）時，先掃一眼本清單，確認該事項是否卡在某個外部依賴上——如果是，可以先做該事項中「不依賴外部回覆」的部分（多數事項都設計成有 workaround 或部分可先行），並同步把對應的問題丟給內容方／API 方，不必等到全部回覆到齊才開工。

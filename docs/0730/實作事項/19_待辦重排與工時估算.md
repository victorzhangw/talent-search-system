## 1. 決策紀錄：事項 16 串流架構（2026-08-05 客戶裁定）

**採用方案：分段緩衝閘門（原選項 A 的改良版）。** 檢查點從「全部輸出完之後」移到「**每一段顯示之前**」。

```
LLM 逐 token 產出
   → 後端累積到一個「段」邊界為止（使用者感受到約 1–2 秒暫存）
   → 對該段跑出口掃描（掃描本身 0.23 ms）
   → 乾淨 → 以打字機效果送出該段
   → 命中 → 把該段＋「不能出現的詞」丟回 LLM 只改寫該段（約 1–2 秒）
           → 重新掃描 → 乾淨才顯示
```

**這個方案解決了什麼**：使用者從頭到尾看不到任何內部標記，也沒有「畫面清空重來」；打字機的即時感保留，代價只是每段前多 1–2 秒的暫存。原本「整篇緩衝」會讓第一個字延遲到整篇生成完，這個方案把延遲切碎成每段一次。

### 1.1 這個決策帶來的新問題（需要一併裁定，否則實作會卡）

| # | 問題 | 說明 | 建議做法 |
|---|---|---|---|
| A | **「段」的定義** | 掃描器是對整段文字跑正則，必須有確定性的切段規則 | 空行分段；另設長度上限（例如 400 字），超過則在句號處提前切，避免長段落把暫存時間拉到 5 秒以上 |
| B | **跨段邊界的洩漏** | 內部標記可能剛好被切在兩段之間（例如 `CIA_` 結尾、下一段開頭 `05`） | 掃描時帶入前一段末尾 N 字元的重疊窗，成本可忽略 |
| C | **完整性檢查仍是整篇層級** | `expected_sections`／1000 字／佐證措辭都要看完整回答，無法逐段判定 | 改為**增量累計**：逐段記錄已出現的段落標題，結尾才判定 |
| D | **完整性不過時無法收回已顯示內容** | 原規格是「重生一次」，但分段模式下前面的段落使用者已經看到 | 建議改為「**生成缺少的段落並附加**」而非重生整篇 |
| E | **某段重寫多次仍不乾淨要怎麼辦** | 前面的段已顯示，無法整篇擋下 | 建議：單段重寫上限 2 次，超過則停止後續輸出並顯示轉人工訊息 |
| F | **`blocked` 的語意改變了** | 原規格「不得把該回覆回傳前端」在分段模式下只能做到「該段與其後不再顯示」 | **需明確告知客戶**：已顯示的段落無法收回，安全承諾的措辭要跟著調整 |

> D、E、F 三項是這個決策**直接造成**的規格落差，不是實作細節。F 尤其重要：不能讓「有掛出口掃描器」被理解成「使用者絕對看不到任何洩漏」。

### 1.2 實作要點（避免踩雷）

- **掃描器每請求建置一次、跨段重用**。0.23 ms 是掃描成本；建置成本（編譯 84 個特質名＋266 個標籤的動態詞表）不能每段重跑。
- **重寫呼叫要帶 per-request 的禁詞清單**，不是全域 350 個詞，否則誤攔率上升。
- **重寫只改單段會有前後不連貫的風險**（第 3 段引用第 1 段的說法）——這是本方案已知的取捨，建議在重寫 prompt 中附上前一段作為上下文。
- **audit 結構要擴充**：原本 `retry_count: {leakage, completeness}` 不夠，需要逐段紀錄（段序、命中詞、重寫次數、最終狀態）。

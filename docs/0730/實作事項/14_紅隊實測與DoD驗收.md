# 14. 紅隊實測與 DoD 驗收

**類型**：驗收測試｜**優先度**：P3（上線前最後一關，需先完成事項 07–12）｜**依賴**：07, 08, 09, 10, 12

## 目標

以標記最密的受測者資料（特質數最多、跨測驗最多的組合，例如全人型四測驗案例）實際打包並呼叫 LLM 數十次，統計出口掃描器（事項 09）攔截後的「內部標記殘留率」，作為最終放行標準。

## 驗收標準（逐字引用，貫穿多份文件、口徑一致）

`b_打包規則_v2_20260727.md` §7：「放行標準：紅隊實測內部標記殘留 0。」

`00_外包交接說明.md` 驗收 DoD 第 4 條：「**出口掃描掛上**：b §7 掛 `exit_scanner_wordlist`，per-request 動態縮小；**紅隊實測內部標記殘留＝0 才放行**。」

`01_設計總說明與決策定案_v2_20260728.md` §5.3：「**紅隊實測**：以標記最密的受測者資料打包，實呼叫 LLM 數十次，出口掃描器統計殘留率；**通過標準＝內部標記殘留 0**。」

三份文件口徑完全一致，沒有模糊空間：**通過線是 0，不是「低於某個百分比」**。

## 為什麼獨立列一項而不併入 09

事項 09 是「出口掃描器要正確攔截」的**單元/整合測試**（構造已知會洩漏的假回答，驗證掃描器抓得到）；本事項是**真實 LLM 產出**的統計驗證——LLM 實際生成的回答可能用你事先沒想到的方式洩漏（例如換句話說但語意等價的洩漏方式），這是掃描器規則覆蓋度的實戰測試，兩者測的對象不同（掃描器邏輯本身 vs. 掃描器對真實 LLM 產出的覆蓋率），且本項需要真實 LLM API 呼叫預算與時間，通常會排在功能開發完成後、上線前最後執行。

## 執行方式建議

1. 挑選/構造 1–2 位「標記最密」的受測者資料（建議用 `新版LOG範例_全人型_雙測驗_v7.txt` 或更密的四測驗組合，全人型模式下所有交互全注入，是洩漏機率最高的壓力測試情境）。
2. 對每一題（含全人型與至少幾題匡列型代表）各呼叫 LLM 數十次，蒐集全部回答。
3. 對每份回答跑事項 09 的出口掃描器，統計「命中洩漏」的回答數 / 總回答數。
4. 目標：0 筆殘留。若有殘留，回頭分析是規則覆蓋不足（回事項 09 補規則）還是 LLM 對某類 prompt 特別容易洩漏（可能需要調整 System 規範用詞，但這屬於內容方管轄，見職責邊界）。

## 範圍邊界

- 本事項只驗證「洩漏是否為 0」，不是對 LLM 回答的內容品質做主觀評分——內容品質評分屬於 `README_最終交付.md` 提到的另一個獨立工作包（「上線前複測」，Codex 生成＋Gemini 品質評分），**不含在本交付包／本次事項拆解範圍**。
- 需要實際 LLM API 額度與呼叫預算，執行前建議先確認要用哪一個模型/環境跑（正式環境 LLM，還是測試沙盒）。

## 驗收標準

- [ ] 至少覆蓋 1 個全人型案例 + 3 個代表性匡列型案例（含至少 1 個含校準特質 A 段的案例）。
- [ ] 每案例呼叫 LLM ≥30 次（「數十次」的具體門檻由你或內容方裁定，30 為建議下限）。
- [ ] 統計報告列出：總呼叫數、洩漏命中數、命中內容摘要（若有）。
- [ ] 最終殘留數＝0 才視為本項與整包功能通過驗收。

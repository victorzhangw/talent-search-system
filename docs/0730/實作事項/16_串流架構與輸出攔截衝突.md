# 16. 既有串流架構與「出口掃描後才能放行」的衝突

**類型**：架構決策（需要你或內容方裁定，非單純技術實作）｜**優先度**：P1（在事項 09/12 真正上線前必須解決，但不阻擋這兩項的邏輯先行開發）｜**依賴**：09（出口掃描器）、12（重生與人工轉介流程）

## 這是什麼問題

這一項是在複查既有程式碼時發現的，之前的事項拆解沒有涵蓋，是後續補充。它不是某個檢查邏輯寫得對不對的問題，是**兩個既有設計目標互相衝突**：

- **現有產品體驗**：`BackEnd/api_v2/routes/chat.py` 第 391–439 行，LLM 回答是逐 token 即時透過 SSE 串流送到前端（`for chunk in response_stream: ... yield f"data: {json.dumps({'type':'token','content':content})}\n\n"`），使用者看到的是「打字機」逐字出現的效果，這是現在的使用者體驗設計。
- **客戶新規格的安全要求**：`b_打包規則_v2_20260727.md` §7 明文「命中＝重寫或遮罩後重送，**直到掃描乾淨才可放行**」「若最終仍有洩漏，**不得把該回覆回傳前端**（阻擋並落人工）」。

問題在於：**要判斷「這段回答有沒有洩漏」，必須先看到完整回答**，出口掃描器（事項 09）是對整段文字跑正則比對，不是能逐 token 判斷的東西。但現行架構是「LLM 吐一個 token，立刻轉送一個 token給前端」——等你收滿全部 token、跑完掃描、判定「這次有洩漏」時，使用者的瀏覽器上早就已經顯示完整段落了，**技術上已經來不及擋**，「不得回傳前端」這句話在現行架構下做不到。

## 為什麼要獨立列一項，而不是寫在事項 09 或 12 裡帶過

因為這不是「9 和 12 要多寫幾行程式碼」，是**要不要改變使用者看到答案的方式**這個產品層決策，牽動的範圍包括：前端等待體驗（要不要接受從「打字機」變成「轉圈圈後一次跳出」）、平均回應延遲感受（使用者原本第一個字很快出現，改成要等模型講完整段才看到東西，感受上變慢，即使實際 token 生成時間一樣）、以及要不要做折衷方案。這件事一旦動了，會同時影響 `chat.py`、事項 09、事項 12 三處程式碼，值得在動工前先讓你知道有這個取捨，而不是等實作到一半才發現卡住。

## 可能的做法（列出選項，不替你決定）

**選項 A：完全緩衝（最貼合客戶規格）**
後端等 LLM 完整回答生成完畢，跑完出口掃描＋完整性檢查＋（必要時）重生一次，確認 `ok` 之後才一次性把整段答案送給前端（或送前端後由前端模擬打字機效果播放，體驗上仍可以做出「像在打字」的感覺，只是資料其實已經到齊）。
- 優點：完全符合「未掃描通過不得回傳」的規格文字，`blocked` 狀態可以真正做到「使用者完全看不到」。
- 缺點：使用者要多等「LLM 生成完整段時間＋掃描時間」才看到第一個字，原本「秒出字」的體感會消失。

**選項 B：邊串流邊背景掃描，事後補救（風險較高，不建議作為預設）**
維持現行逐 token 送出，但同時在後端累積完整文字背景跑掃描；若最終判定有洩漏，只能在訊息紀錄裡標記、事後轉人工複核，**無法阻止使用者已經看到的內容**。
- 優點：使用者體驗不變。
- 缺點：規格「不得回傳前端」實質上做不到，只能退化成「回傳了但事後知道有問題」，安全承諾打折。

**選項 C：僅對「快速提問（題庫題）」走緩衝模式，「自由提問」維持現行串流**
題庫題的洩漏風險與稽核要求通常更高（有固定的 `expected_sections` 要檢查、涉及正式報告情境），自由提問相對彈性；可以只在題庫題路徑套用選項 A，自由提問維持現行體驗。
- 優點：折衷，先在風險較高的路徑補上防線。
- 缺點：兩套路徑行為不一致，維護與測試成本較高；且自由提問一樣可能問到受測者特質，一樣有洩漏風險，只是規格文字沒有專門提及。

## 這件事不阻擋其他事項先開工

事項 09（出口掃描器邏輯本身）、事項 10（完整性檢查邏輯本身）、事項 12（重生與狀態機邏輯本身）都可以先按各自文件的規格完整實作與單元測試，這些邏輯本身跟「怎麼送到前端」無關。**真正卡住的只有「最終要不要真的把 `blocked` 的內容擋下來」這一步**——在你／內容方對本事項的選項做出決定之前，`blocked` 狀態可以先做到「在後端記錄、在事項 12 的 audit log 裡標記」，但不代表使用者端真的看不到，這一點在正式上線前必須說清楚，不能讓「有掛出口掃描器」被誤解成「使用者絕對看不到洩漏內容」。

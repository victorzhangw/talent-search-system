# 09. 出口掃描器（b§7，9 類硬樣式 + everyday 白名單）

**類型**：品質關卡｜**優先度**：P1｜**依賴**：07（LOG 組裝，取得本次注入的名稱/標籤）

## 目標

LLM 回答產出後，掃描是否洩漏任何內部標記（特質代號、band 字母、分數、聯動語、內部欄名格式等）；命中即擋下不得回傳前端。這是整包規格中「對外乾淨」的最後一道防線。

## 規則來源（逐字引用 `b_打包規則_v2_20260727.md` §7）

> 掛 `exit_scanner_wordlist_v6_2.json`：**9 類硬樣式**（trait_id／band_code／聯動／分數洩漏／中文分區／HR 決策語／人口統計／誠信定罪／label 判定，以 `hard_patterns` 實際條目為準）＋特質名＋band 標籤；**per-request 動態縮小**（只掃本次實際注入的名稱與標籤）；everyday_words 只擋構念式用法。命中＝重寫或遮罩後重送，**直到掃描乾淨才可放行**；洩漏重試與 §8 段落缺漏的 1 次重生**分開計數**。若最終仍有洩漏，**不得把該回覆回傳前端**（阻擋並落人工）。放行標準：紅隊實測內部標記殘留 0。

對照 System 規範甲類（`a_LOG完成版模板_v2_20260727.md` §甲，1–4 條）——出口掃描器要攔的正是這四類：內部代號/band 字母/分區字樣/分數；特質名稱與 band 標籤原文；「聯動」「連動」「交互作用」等推理鷹架語；方括號標頭格式與欄名整行照抄。

實際載入 `exit_scanner_wordlist_v6_2.json` 驗證，以下數字與路徑全部屬實，實作時可直接寫成單元測試的期望值：

`everyday_words`（20 詞，全文）：企圖心、信任、公正性、可靠性、同理心、好奇心、審慎、希望、情緒反應、感謝、承諾、挑戰、時間壓力、樂觀、真實性、義務感、自律性、衝動管理、誠懇、韌性

## 關鍵坑 1：everyday 白名單是巢狀鍵，取錯路徑會全部誤攔

`02_參考程式碼_打包器骨架.py` 第 334–351 行 `load_everyday_whitelist()` 的註解已經寫得非常明白：
> ⚠ 這兩個鍵是**巢狀**的，不在頂層：`trait_names_blocklist.everyday_words`（20 詞，如「信任」「同理心」）、`band_labels_blocklist.everyday_labels`（4 詞）。取錯路徑會得到空集合 → 84 個特質名與 266 個標籤全部硬攔 →「展現韌性」這類日常語用被判洩漏、每次重生落人工。

`00_外包交接說明.md` 常見誤區也單獨列了這條，優先度很高——這是一個**取錯一個 JSON path 就會讓功能整個不可用**的陷阱，實作時務必寫單元測試鎖住這個路徑。

## 關鍵坑 2：guard regex 目前漏抓「很高／較高」等常見說法（已在 `_ LOG 實作補充說明 for victor.txt` 中被指出，需要補強）

參考骨架第 314 行給的判定式：
```python
guard = r"(?=[偏程度分高低強弱]|傾向|指標|區間)"
```
這是「詞 + lookahead 下一個字元是『偏程度分高低強弱』其中之一，或接『傾向/指標/區間』」。**它只在特質名/標籤詞後面緊接著這些字時才觸發**，遇到中間插了「很」「較」「相對」等副詞時會漏抓：
- 「韌性偏高」✅ 攔得住（「偏」緊接在後）
- 「韌性很高」❌ 攔不住（「很」不在字元集合內，lookahead 在「很」處失敗）
- 「信任度低」是否攔得住需視「信任度」是否被當一個詞匹配，若白名單詞是「信任」則「信任度低」中「信任」後接的是「度」，同樣落空
- 「情緒反應相對較強」❌ 攔不住

這與 `_ LOG 實作補充說明 for victor.txt` 第三節「目前 regex 需要補強」的觀察完全一致：
> 現有規則可以攔截：韌性偏高、快速轉換傾向。但可能漏掉：韌性很高、韌性較高、信任度低、情緒反應相對較強。這些仍屬於程度或高低判定，應納入攔截測試。

### 實測結果（2026-07-31 第二次複查，不再是推測）

拿規格驗收表的句子對現行 guard regex 實跑，**9 個案例中有 3 個不符規格**：

```
句子                期望   現行regex  結果
面對挑戰時展現韌性     放行    放行      OK
韌性偏高             攔截    攔截      OK
韌性很高             攔截    放行      <<< 不符
韌性較高             攔截    放行      <<< 不符
建立團隊信任          放行    放行      OK
信任程度偏低          攔截    攔截      OK
情緒反應可能較明顯     放行    放行      OK
情緒反應分數較高       攔截    攔截      OK
情緒反應相對較強       攔截    放行      <<< 不符
```

**本事項必須把 guard regex 改成能容忍中間插入副詞的寫法。** 下列改法已實測驗證：

```python
guard = r"(?=[很較相對更]{0,3}[偏程度分高低強弱]|傾向|指標|區間)"
```

用 14 個案例（規格驗收表 11 條 ＋ 額外 3 條防誤攔案例：「這個挑戰很大」「他願意表達感謝」「團隊需要承諾」皆須放行）實跑比較：

| | 通過數 | 不符案例 |
|---|---|---|
| 現行 regex | 11 / 14 | 韌性很高、韌性較高、情緒反應相對較強 |
| 上述建議 regex | **14 / 14** | 無 |

關鍵在於這個改法**沒有把「很/較/相對」本身當成攔截條件**，而是允許它們出現在特質詞與程度字之間——所以「這個挑戰很大」（「大」不在程度字集合內）仍正確放行，不會為了補抓而製造新的誤攔。

> 仍需注意：上述只驗證了規格列出的案例。正式實作時建議再依 `exit_scanner_wordlist_v6_2.json` 全部 84 個特質名 + 266 個標籤跑一次大規模回歸，確認沒有其他詞在真實語料中產生誤攔（例如「希望很高」這類詞本身即為日常用語與構念名撞名的邊界情況，可能需要個案處理）。

## per-request 動態縮小

只掃本次實際注入的特質名稱與 band 標籤（來自事項 05/06 的 audit 資料），不是全域 113 特質全掃——這樣「未注入的名稱」不會誤報，也能縮小掃描範圍。參考實作見 `02_參考程式碼_打包器骨架.py` 第 309–332 行 `build_exit_scanner()`。

## 補充核對（2026-07-31 複查）：現有系統目前完全靠「事前提醒 LLM」，沒有事後掃描這道防線

現有 22 個模組 prompt 檔案（如 `BackEnd/api_v2/prompts/modules/mgmt_pressure_single.txt` 第 39–47 行「輸出安全防護」段）目前的防洩漏策略，是**在 prompt 裡直接列出黑名單詞，拜託 LLM 不要輸出**：
```
【輸出安全防護】
嚴禁在回覆中出現以下任何內容：
- 特質名稱（如：完美主義、創新力、韌性、盡責、同理心…）
- Band 等級（如：A、B、C 或 Band A）
- 特質分數（如：35分、7分）
...
```
`context_builder.py` 也在輸入端做了一部分防護（用 `semantic_label` 取代原始特質名、剝除交互開頭句）。但**目前整條 pipeline 裡，沒有任何一處在 LLM 真正生成回答之後再檢查一次**——完全依賴「事前用文字提醒 LLM 不要講」這一種防線，而 LLM 本來就不保證 100% 遵守指令性禁令，這正是客戶規格要新增出口掃描器（事後、確定性、程式碼層面攔截）的根本原因：**現有做法只有「軟性提醒」，新規格要加上「硬性事後檢查」**，兩者不是二選一，是疊加關係（輸入端仍保留現有的語意隱藏設計，出口再加一道確定性掃描）。

另外，比對現有 22 份模組 prompt 各自寫的黑名單詞彙（如上面「完美主義、創新力、韌性…」這份是 `mgmt_pressure` 自己列的），**每個模組列的清單不保證彼此一致、也不保證涵蓋 113 個特質全集**——這也是事項 07 第 2 點提到「22 份重複禁令段」問題的具體症狀之一。導入 per-request 動態縮小的出口掃描器後，這些模組各自維護的黑名單段落可以整段移除，改由掃描器統一、完整地涵蓋本次注入的全部特質名/標籤，不再依賴每個模組作者手動列全。

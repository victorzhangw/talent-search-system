## 這包文件要達成的目標（一句話）

把「特質敘事文件（內容正本）× 某受測者的特質評鑑結果（Talent Chat API v2）× 快速提問題庫」，用**零語意、純機械**的規則組裝成一份可直接送給 LLM 的 LOG payload；再掛上出口掃描與輸出完整性檢查，確保回傳前端的內容不洩漏任何內部代號／分數／標籤。

這是全新功能——目前 repo（`BackEnd/api_v2/`）已有 Talent Chat API v2 的路由（`candidates.py`／`modules.py`／`reports.py`／`chat.py`）與既有的 RAG prompt 系統（`prompts/*.txt`），但**完全沒有**這份規格描述的「LOG 打包器」「出口掃描器」「輸出完整性檢查」——這些字串在整個 `BackEnd` 都搜不到任何既有實作。也就是說：這是要新建的一條 pipeline，不是修改既有功能。

## 修訂紀錄

**2026-07-31 第一次複查**：初版拆解時只讀了客戶交付文件，沒有深入比對本 repo 既有程式碼。複查後發現本 repo 其實已有相當一部分基礎建設（`trait_definitions`/`trait_bands`/`trait_interactions` DB 表、既有 22 個快速提問模組、既有的交互敘事剝除正則、既有的語意隱藏設計），也發現了新規格與既有架構之間幾個實質衝突（現有程式碼自己重算 band、不信任 API 給的 band；現有逐 token 串流與「出口掃描後才放行」的規則衝突；現有 22 份模組 prompt 各自帶重複的禁令文字）。已將這些發現補進事項 01、02、03、04、06、07、09、12、15，並新增事項 16 專門處理串流架構衝突。標記「補充核對（2026-07-31 複查）」的段落為該次新增。

**2026-07-31 第二次複查（資料檔實測）**：前兩次都是「讀文件」，這次改為**實際載入客戶的 JSON 資料檔與正則、跑程式驗證每個數字與規則**。結果：文件描述的數字全部屬實（9 條 hard_patterns、71 條風險端點、84 特質名、266 標籤、20 everyday_words、4 everyday_labels、3 題空 `expected_sections`、113 特質），但另外挖出三個**照文件做反而會出錯**的陷阱，都已補進對應事項：

| 發現 | 影響 | 補進 |
|---|---|---|
| 客戶 `regex_pack` 的開頭句正則**比既有程式碼的窄**，對「雙特質串接」格式完全不匹配——照客戶文件替換既有正則會造成 trait_id/特質名/band 三重洩漏的 regression | 高 | [02](02_資料層讀取_交互敘事正本與規則剝除.md) |
| `injection_set` 欄位（名字最像「要注入的集合」）**已內含三個校準特質**，誤用它當全塊區來源會把校準特質錯誤升級成完整區塊，違反核心規則 | 高 | [05](05_特質區塊分流邏輯.md)、[06](06_交互選列邏輯與風險端點表.md) |
| everyday guard regex 實測**9 個規格案例中 3 個不符**；已驗證出一個 14/14 全過且不製造新誤攔的修正寫法 | 中 | [09](09_出口掃描器.md) |

另補：客戶 `regex_pack` 共 5 條規則而既有程式碼只實作 1 條（02）；客戶自己的資料檔佐證了事項 01 找到的 `MUST DO: ['…']` bug 並指明正解（01）；`expected_sections` 資料方自標為 best-effort 且有過「誤抽導致某題恆判失敗」的前例（10）；`construct_families_v1.json` 確認含 SDR 校準族，佐證「不得在 runtime 做家族擴張」（05）。標記「第二次複查」的段落為本次新增。

## 職責邊界（貫穿所有事項，來自 `00_外包交接說明.md`）

- **只做機械組裝**：集合查找、去重、分組、字串拼接。零語意判斷。
- **不改動任何文字**：指令文字、特質敘事、交互敘事，原樣複製，一字不改。
- **不自行擴張匡列範圍**：匡列集合是題庫表給的資料，不是程式算的邏輯；構念家族補全已在資料生成期做完，打包層不得再做一次。
- **語意疑義一律回問內容方（Traitty 團隊）**，不自行詮釋、不改資料。

# 02. 資料層讀取：交互敘事正本（08 分頁）讀取 + regex_pack 剝除 adapter

**類型**：基礎資料層｜**優先度**：P0｜**依賴**：無

## 目標

實作 `load_interactions()`：從內容正本 `0722 02_08 V6.2 spec_.xlsx` 的「08」分頁讀出每一列交互敘事，解析出兩端 `(trait_id, band)` 與敘事本文，並在載入時對本文套用 `regex_pack_v6_2.json` 的規則，剝除敘事開頭的配對句與殘留代號。

## 背景

參考程式碼骨架第 102–106 行：
```python
def load_interactions(pkg, strip_rules) -> list:
    """TODO(外包): 從 spec xlsx『08』分頁讀每一列交互，回傳 list[Interaction]。
    每列需解析出兩端 (id, band) 與敘事本文；載入時對本文套 strip_rules（regex_pack）剝除開頭配對句與殘留代號。
    row＝該列在 08 的原始序（0 起算，供去重與選列排序）。"""
```

`Interaction` 資料結構已定義好（骨架第 49–56 行）：
```python
@dataclass
class Interaction:
    a_id: str; a_band: str
    b_id: str; b_band: str
    text: str   # 敘事本文；載入時已跑 regex_pack 剝除開頭配對句與殘留代號
    row: int    # 08 原始列序（供鏡像去重與選列排序）
```

## 為什麼要剝除開頭句

08 分頁的敘事本文原始格式帶有「與 XXX_nn (名) Y聯動：」這種開頭句——配對資訊已經上移到組裝後的標頭 `[交互 | CIA_16_A × CIA_18_A | 目標路徑清晰 × 逆境復原快]`，敘事本文裡不該再重複，且「聯動」字樣本身就是 System 規範甲類第 3 條明令禁止外流的推理鷹架語。這個剝除規則屬於**內容資料生成期已定義好的機械規則**（存在 `regex_pack_v6_2.json`），本事項只是套用，不是自己設計正則。

## 輸入輸出契約

**輸入**：`0722 02_08 V6.2 spec_.xlsx` 08 分頁（每列＝一組交互配對＋敘事文字）；`regex_pack_v6_2.json` 的 `rules`（`pattern`/`replace` 陣列）。

**輸出**：`list[Interaction]`，`row` 為 08 分頁中的原始列序（0 起算），供事項 06 的鏡像去重與選列排序使用。

## 範圍邊界

- **不自己設計新的剝除規則**——`regex_pack_v6_2.json` 是唯一來源，只套用不擴充。
- **每列必須保留原始列序**，因為交互選列的鏡像去重規則是「同一無序配對取列序在前者」（見事項 06），列序錯了去重結果就錯。
- 標頭用的 `trait_id`／band（如 `CIA_16_A`）**不在剝除範圍內**，只有敘事本文欄位套用 strip_rules；這點會在事項 08（單元檢查第 3 項）再次強調，避免誤剝標頭。

## 驗收標準

- [ ] `load_interactions()` 回傳的每筆敘事本文開頭不再出現「與 XXX_nn (名) Y聯動：」樣式字串。
- [ ] `row` 欄位與 08 分頁實際列序一致（抽樣核對前 5 筆與後 5 筆）。
- [ ] 敘事本文中不含 `regex_pack_v6_2.json` 規則要剝除的殘留代號樣式。
- [ ] 用兩份 `新版LOG範例_*_v7.txt` 中出現的任一交互塊敘事本文，反查 08 分頁對應列，確認剝除後文字與範例檔逐字一致。

## ⚠ 最高優先警告（2026-07-31 第二次複查實測）：直接用客戶的 `strip_opening_clause` 取代既有正則，會造成洩漏regression

實際打開 `regex_pack_v6_2.json` 比對後發現：**客戶的開頭句剝除正則比既有程式碼的更「窄」，會漏掉一種真實存在的敘事格式。**

| | 正則 |
|---|---|
| 客戶 `strip_opening_clause` | `^與 ?[A-Z]{3}_\d+ ?[（(][^)）]+[)）] ?(高分\|低分\|[ABC]) ?聯動[：:]\s*` |
| 既有 `_INTERACTION_LEAK_PREFIX_RE` | `^與\s*[A-Za-z]+_\d+.*?[：:]\s*` |

關鍵差異：客戶的正則**要求 band 後面必須緊接著「聯動」兩個字**；但既有程式碼的註解記載了一種**沒有「聯動」字樣的雙特質串接格式**（並註明已對全部 2,389 列確認過）：

```
與 CIA_06 (條理性) C 與 CIA_07 (完美主義) A：實際敘事開始…
```

實測兩個正則對這行的處理結果：

```
IN  : 與 CIA_06 (條理性) C 與 CIA_07 (完美主義) A：實際敘事開始…
  客戶正則  -> NO MATCH（前綴原封不動留著）
  既有正則  -> STRIPPED: 實際敘事開始…
```

也就是說，**如果實作時「照客戶交付的 regex_pack 辦事」把既有正則換掉，這類敘事的 `CIA_06 (條理性) C 與 CIA_07 (完美主義) A` 會原封不動被送進 LLM payload**——裡面同時包含 trait_id、中文特質名、band 三種內部標記，正是整套規格最核心要防的洩漏類型。這是一個「照著客戶文件做反而會退步」的陷阱。

**正確做法＝取兩者的聯集，不是取代**：保留既有較寬鬆的開頭句正則（或合併成一條能同時涵蓋兩種格式的），再補上客戶 regex_pack 的其餘規則（見下）。實作後務必用上面那行串接格式當回歸測試案例。

> 這個差異也值得回報給內容方（依 `00_外包交接說明.md` §六升級路徑：「你發現資料表本身矛盾→回報內容方，不要自行修正資料」）——客戶的 regex_pack 可能是依 08 分頁的**主要**格式寫的，沒有涵蓋串接例外；但既有程式碼的註解聲稱已核對過全部 2,389 列。兩邊說法需要對齊，建議請內容方確認 08 正本中究竟有多少列屬於串接格式。

## 客戶 regex_pack 共 5 條規則，既有程式碼只實作了第 1 條

| # | id | 用途 | 既有程式碼有嗎 |
|---|---|---|---|
| 1 | `strip_opening_clause` | 剝除 08 敘事開頭配對句 | ✅ 有（但如上所述覆蓋範圍不同） |
| 2 | `strip_paren_codes` | 清除本文殘留括號代號，如「渴望成長（31）」→「渴望成長」 | ❌ 沒有 |
| 3 | `strip_trait_id_refs` | 本文內裸露的內部 ID（防禦性，正常不應存在） | ❌ 沒有 |
| 4 | `strip_python_list_wrapper` | 去除 MUST DO 欄位的 Python list 字串包裝 | ❌ 沒有（相關 bug 見事項 01） |
| 5 | `strip_empty_parens` | 人名後空括號 `()` | ❌ 沒有 |

規則 2、3、5 是本事項要補的；規則 4 依客戶自己在 JSON 裡的註記「**建議改為直接讀原欄位文字而非 repr；此 regex 僅為救急**」，應該在事項 01 從資料讀取層根治，而不是靠正則事後補救。

> 注意規則 3 的 `note`：「**只適用於敘事本文欄；標頭欄位的 ID 必須保留（程式匡列用）**」——這與事項 08 單元檢查第 3 項的警告是同一件事，套用範圍務必只限敘事本文欄位。

## 補充核對（2026-07-31 複查）：既有程式碼已有一版簡化的剝除邏輯，需要對齊而非重寫

`BackEnd/api_v2/services/context_builder.py` 第 31–43 行已經存在功能類似的處理：
```python
# trait_interactions.narrative is authored as "與 {trait_id} ({name_zh}) {band}聯動：{actual text}"
# (sometimes chaining a second trait, e.g. "與 CIA_06 (條理性) C 與 CIA_07 (完美主義) A：...")
_INTERACTION_LEAK_PREFIX_RE = re.compile(r'^與\s*[A-Za-z]+_\d+.*?[：:]\s*')

def _strip_interaction_leak(narrative):
    if not narrative:
        return narrative
    return _INTERACTION_LEAK_PREFIX_RE.sub('', narrative, count=1)
```
這代表交互資料一樣早就進了 `trait_interactions` DB 表（`BackEnd/scripts/migrate_traits_from_excel.py`），且已有一版**單一正則**在剝開頭配對句（含註解提到雙特質串接的邊界情況）。**本事項不是從零蓋一個 xlsx 08 分頁讀取器，而是要核對：這個既有正則的覆蓋範圍是否等同 `regex_pack_v6_2.json` 的完整規則集**（客戶正則可能不只一條、覆蓋更多殘留代號樣式），若既有正則覆蓋不足，要補齊規則而不是整套重寫；若兩者本來就等價，這一項工作量會小很多。

另外，`row`（08 原始列序，供事項 06 鏡像去重排序用）目前的 DB schema（`TraitInteraction` 表，見 `BackEnd/api_v2/database/models.py`）**沒有保留原始列序欄位**（只有自增 `id`，不保證等於 08 分頁列序）。若匯入時 `id` 剛好依 08 列序遞增寫入，可以直接借用；否則需要匯入管線額外記錄一個 `source_row` 欄位，這是本事項要確認的資料面缺口。

# b. 打包規則 v2.0（2026-07-27）——動態篩選人選資料與匡列特質的程序

> 讀者：LOG 打包（匯出）程式的實作團隊。
> 原則：本程序**零內容邏輯、零語意判斷**——全部是集合查找、去重、分組；語意都住在引用的資料表裡。
> 產出的 LOG 樣式見 a 文件第二部分；規範文字（System 與六條判讀規範）為靜態常數，由 a 文件複製。

## 0. 引用的資料表（單一來源）

| 表 | 檔案 | 內容 |
|---|---|---|
| T1 題庫表 | c_快速提問重構版 xlsx →導出 question_injection_table JSON | 每題：型別（匡列型／全人型）、對象（單人／多人）、四測驗匡列特質 ID、清理後指令文字 |
| T2 風險端點表 | question_injection_table JSON `risk_endpoints.adopted`（71 端點） | (trait_id, band) 對；受測者落在端點＝「命中」 |
| T3 校準特質 | 固定三元素 {CIA_33, ANI_23, SPA_12} | |
| T4 內容正本 | 0722 02_08 V6.2 spec_.xlsx | 02 分頁＝特質欄位；08 分頁＝交互敘事 |
| T5 剝除正則 | regex_pack_v6_2.json | 開頭句剝除等 |

## 1. 輸入

- 受測者：姓名、受測者 ID、已完成測驗清單、每特質分數→band（A/B/C）。
- 本次題目 ID（快速提問）；或「自由提問」旗標＋**使用者原始提問文字**（自由提問時必附，供組 [任務指令] 與 S1 判讀範圍）。

### 1.1 輸入 schema（外包實作契約）
```
{
  respondent: { name: str, id: str, tests: [ "ANI"|"CIA"|"SPA"|"CSR" ], scores: { trait_id: "A"|"B"|"C" } },
  mode: "quick" | "free",
  question_id: str,        // mode=quick 時必填，對應題庫表
  user_query: str          // mode=free 時必填，使用者原始提問
}
多人情境：respondents: [ {…}, … ]，逐人一組 ### 區塊；任務指令用多人欄。
```

> **audience 前置驗證（組裝前必做，不符即拒絕請求）**：題庫表每題有 `audience`＝`single_only`／`multi_only`／`both`。
> 人數與之不符必須**拒絕請求**，不可繼續組裝——`single_only` 題的 `instruction_multi` 是佔位字串「僅適用單人」
> （反之亦然），照組會送出只有 5 個字的壞任務指令。
>
> **`question_id` 值域**：題庫表每題以 `idx`（整數）＋中文 `title` 識別，**沒有獨立 id 欄**。
> 請以 `idx` 為 `question_id`（title 僅供人閱）。與 API `module.id` 的對照表尚未建立（見 03 §3 缺口）。


## 2. 特質區塊分流

```
受測者特質集合 P = {(trait_id, band)}（僅其受測測驗）
匡列集合 S = 題庫表該題的匡列 ID（僅其受測測驗的欄位）；自由提問或全人型題 → S = P 的全部 ID
命中風險端點 R = { t | (t, band_of_t) ∈ 風險端點表 }

全塊區   ＝ S 中的特質：注入四欄原文（行為面向/管理重點/可用於/禁止）＋標頭 [特質 | ID_band | 標籤]
索引區   ＝ P - S：每特質一行「- ID_band｜中文名｜band標籤：行為面向全文」
```

> **欄名正規化（必做）**：02 正本的 `ai_do`／`ai_dont` 儲存格**部分已自帶**「可用於：」「禁止：」前綴
> （實測：ANI 69/69、CIA 108/108、CSR 108/108 自帶；**SPA 僅 1/54**）。程式須「**缺則補、有則不重複加**」，
> 否則 CIA/ANI/CSR 會輸出「可用於：可用於：…」，而 SPA 會缺欄名。
> 資料面根治＝正本補齊 SPA 53 列前綴（已列為待修資料項，見 README 待辦）。

注意：風險特質與校準特質**不因此升全塊**；未匡列時留在索引區（其行為面向已自帶所需語意）。

## 3. 交互選列（統一原則：**相關的全注入、不做任意砍量、無條數上限**）

候選：08 分頁中「配對兩端 (ID, band) 都 ∈ P」的列；鏡像去重（同一無序配對取列序在前者）；敘事開頭「與 XXX_nn (名) Y聯動：」依 T5 剝除。

> **兩模式同一原則**：把「相關的交互」全部注入、不縮減、不設條數上限；由 System S2§15 讓 LLM 自濾。差別只在**匡列型多一道題意過濾**（有 S），全人型沒有（全部特質都是主體，全部候選都相關）。

**匡列型（兩步）：**
```
1. 題意過濾：至少一端 ∈ (S ∪ 校準 ∪ R)（濾掉兩端都與本題無關的配對）
2. 過濾後全部注入，依列序，分兩個子區塊：
   「交互作用——本題相關」：至少一端 ∈ S 的列
   「交互作用——作答校準與風險提示」：僅因 校準/R 入選的列
```

**全人型／自由提問（兩步，2026-07-28 用戶裁定改為全注入）：**
```
1. 不做題意過濾（S＝全部特質，所有候選都相關）。
2. 候選全部注入，依列序，分兩個子區塊：
   「交互作用——作答校準與風險提示」：觸及 (校準 ∪ R) 的列（排前，讀的顯著性高）
   「交互作用——其他參考」：其餘全部
（全人型不出現「本題相關」子區塊；全注入自然覆蓋每個有候選的特質——不需覆蓋/補充步驟）
```

> **不設任何條數上限或體積防呆（用戶裁定）**：候選池天生有限（無跨測驗交互，雙測驗約 136、四測驗上限約 300–450），不會爆炸；全人型深度題稀少且高價值，值得完整注入。舊版「覆蓋＋補充10＋>90 截斷」為砍量設計，已作廢——它讓全人模式反而比匡列模式不完整（本末倒置），故移除。

**註記（程式自動加）：**
- 匡列型「本題相關」子區塊 **1–4 條** → 尾註「本題相關交互較少，判讀以特質區塊為主」；**0 條時該子區塊整段不輸出**（不加尾註）。
- 全人型全注入，**無「未注入」尾註、無截斷**（不再發生）。

## 4. 校準送達（零工序，僅為說明）

社會期望反應的校準由資料自帶，程式不需任何動作：全塊時四欄自帶完整指令；索引時行為面向尾句自帶可信度句；System 靜態規則見到標籤即全域生效。

## 5. 組裝順序

```
[SYSTEM PROMPT]（a 文件第一部分，靜態常數）
---
## 【輸入數據】
### [受測者 | 姓名 | ID]          ←（網站基本欄位為保留擴充位，目前不輸出）
#### 判讀主體特質                    ←匡列型用此字串
#### 判讀主體特質（全人型＝全部特質）  ←全人型用此字串
#### 其他特質索引（僅供關聯參考，非本題判讀主體）
#### 交互作用——本題相關（匡列型）
#### 交互作用——作答校準與風險提示
#### 交互作用——其他參考（全人型）
---
[任務指令]（題庫表該題清理後指令；多人題用多人欄）
```

多人情境：每位受測者一組「###受測者＋區塊」，依序排列；任務指令用多人欄版本。

## 6. 交付前單元檢查（每次組裝跑）

1. 全塊數 ＝ S∩P 特質數；索引行數 ＝ |P| - 全塊數。
2. 每個交互標頭的兩端 ID 都出現在全塊區或索引區。
3. 全文無 `['`、無空括號 `()`；殘留括號代號檢查**僅適用敘事本文欄，必須排除標頭**——標頭的 `XXX_nn` ID 是合法內部標記且**必須保留**（見 00 DoD 5、regex_pack 的 `strip_trait_id_refs` note）。對全文套 T5 會命中上百個合法標頭 ID，導致檢查必然失敗或誤剝 ID。
4. 子區塊歸屬正確：本題相關列至少一端 ∈ S。

## 7. 出口掃描（LLM 回答後）

掛 exit_scanner_wordlist_v6_2.json：**9 類硬樣式**（trait_id／band_code／聯動／分數洩漏／中文分區／HR 決策語／人口統計／誠信定罪／label 判定，以 `hard_patterns` 實際條目為準）＋特質名＋band 標籤；**per-request 動態縮小**（只掃本次實際注入的名稱與標籤）；everyday_words 只擋構念式用法。命中＝重寫或遮罩後重送，**直到掃描乾淨才可放行**；洩漏重試與 §8 段落缺漏的 1 次重生**分開計數**。若最終仍有洩漏，**不得把該回覆回傳前端**（阻擋並落人工）。放行標準：紅隊實測內部標記殘留 0。

## 8. 輸出完整性檢查（出口掃描器旁掛，確定性規則；PDCA 的 Check 落在輸出端）

> 段落齊全檢查的期望段落＝ question_injection_table 各題 `expected_sections（best-effort 提示，§8 採子集寬鬆判定）`（v7 起機讀化）；多人題另查每位受測者姓名獨立成段。
>
> **空值處理（不可靜默跳過）**：有 3 題（團隊合作的互補與摩擦／打造高效會議團隊／高效溝通模式解析）的指令未定義固定段落標題，其 `expected_sections` 為空並帶 `expected_sections_note`。程式遇空值時**略過段落檢查，但必須 log「本題未做段落齊全檢查（原因：指令未定義固定段落標題）」**——不得無聲通過，否則會被誤讀為「已檢查且通過」。

依本次模式分流：
- **題庫題**：檢查段落標題是否齊全。**唯一來源＝question_injection_table 的 `expected_sections`**（不得自行解析指令文字抽段落——那是語意動作，違反零語意邏輯原則）；多人題另查每位受測者姓名皆出現且各有獨立段落。**不查字數**（長度由架構管）。
- **自由提問**：檢查回答 1,000 字以內（用戶裁定）。
- **共同**：受測者含社會期望反應 A 段時，回答須含佐證類措辭（詞表比對：佐證／行為事例／工作樣本／不以單次）。

不過 → 帶「缺了什麼」的具體原因重生成一次（上限 1 次，再不過落人工）。
註：不採「LLM 自我確認已讀完全部資料」式檢查——自我宣告不可驗證，且與自濾授權（S2 第 15 條）相抵觸。


## 9. everyday_words / everyday_labels 判定規則（配合出口掃描 §7）

這些詞單獨出現＝日常語用，放行；僅當後接程度/分數/高低判定時視為構念式洩漏並攔截。判定 regex：`詞 + (?=[偏程度分高低強弱]|傾向|指標|區間)`。攔截例「韌性偏高」；放行例「展現韌性」。詞表見 exit_scanner_wordlist 之 everyday_words/everyday_labels。

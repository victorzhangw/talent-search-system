## 0. 這支程式做什麼（一句話）

**把「特質敘事文件 × 某受測者的特質評鑑結果 × 快速提問內文」，用確定性規則組裝成一份可直接送給 LLM 的最終 LOG payload；程式只做格式組裝，不生產也不改動任何語意內容。**

### 三類輸入 → 交付包對應

| 你口中的輸入 | 實際檔案 | 程式怎麼用 |
|---|---|---|
| **特質敘事文件** | `0722 02_08 V6.2 spec_.xlsx`（02＝特質欄位、08＝交互敘事）＋ 已導出的 `traits_113_v6_2.json` | 取特質四欄原文組特質塊；取 08 配對列組交互塊 |
| **特質評鑑結果** | 每次請求傳入的受測者資料（姓名／ID／已測測驗／各特質分數→band），schema 見 `b §1.1` | 決定哪些特質、落在哪個 band、命中哪些風險端點 |
| **快速提問內文** | `question_injection_table_v9.json`（`c_快速提問重構版 xlsx` 的機讀版） | 取該題型別／匡列特質 ID／清理後指令文字 |

**輸出**：一份 LOG 檔（`[SYSTEM PROMPT]` ＋ `【輸入數據】`組裝區 ＋ `[任務指令]`），格式見兩份 `新版LOG範例_*_v7.txt`。

## 1. 三層分工（本設計的地基）

**資料正本管「內容正確」／匯出打包管「格式組裝」／runtime 指令管「輸出轉譯」——三層各歸其位。**

- 打包層**零內容邏輯**：只有集合查找、去重、分組、字串拼接。語意全住在資料表裡。
- 內容修正只發生在 `spec xlsx` 正本；正本版本推進（紅標版）→ 觸發重匯，打包程式不持有任何內容邏輯，正本改了就自動生效。
- 對外乾淨由 runtime 輸出規則（a 文件 System）＋出口掃描器保證，**不靠打包層剝內容**。

### 兩個貫穿全案的原則

1. **輸入帶標記、輸出全轉譯**：payload 內保留內部標記（ID／label／band）供 LLM 導航與匹配，對外由輸出規則＋出口掃描器擋。打包層**不剝標記**。
2. **ID＋label 雙標示**：ID（`CIA_22_A`）給程式匡列比對與稽核；label（`自在於無規則`）給 LLM 語意錨定。**單用 ID 對 LLM 不友善；單用 label 會跨測驗撞名、清單腐化（SPA 7/11 錯位為既往實例）。故每個塊都保留 ID——外包不可剝除。**

## 2. 注入塊格式（定案）

### 2.1 特質塊
```
[特質 | CIA_22_A | 自在於無規則]
行為面向：…    管理重點：…    可用於：①…②…③…    禁止：①…②…③…
```
標頭 `[特質 | {trait_id}_{band} | {label}]`；欄名用中文；刪除 `MUST DO: ['…']` 英文鍵與 Python list 包裝；人名標頭空括號移除。

### 2.2 交互塊
```
[交互 | CSR_01_A × CSR_24_C | 卓越進取 × 自我優先]
（敘事本文；開頭「與 XXX_nn (名) Y聯動：」由匯出程式依 regex_pack 確定性剝除，配對資訊已上移標頭）
```

### 2.3 作答校準送達（社會期望反應族專屬；**資料自帶，程式零工序**）

社會期望反應族（**CIA_33／ANI_23／SPA_12**，三份測驗的同一構念）影響「這份自陳該打幾折」，是解讀所有特質的前置校準訊號。但**打包程式不需要合成任何獨立的校準區塊**（早期 v1.1 提案曾設想插入 `[作答校準|…]` meta 塊，定案時已簡化掉——實際範例檔中沒有此塊）。校準靠三條既有管道自動送達：

1. **該特質被匡列** → 照 2.1 出現在特質塊，其四欄原文已含校準指令（可信度打折、援引行為事例）。
2. **該特質未被匡列** → 落在索引區，其行為面向尾句已自帶可信度提示句。
3. 上述之外，該特質的交互列一律進「作答校準與風險提示」子區塊（見 §3 機制）；System 靜態規則見到其標籤即全域生效。

> 對外包的意義：**校準是零工序**。你只要照 §2.1／§2.2 正常組裝，校準內容就已隨資料到位，不要另寫校準邏輯、也不要合成 meta 塊。

### 定案後新增的機制

- **交互選列無「題意截斷上限」**：過濾即預算。匡列型兩步、全人型三步（補充 10／>90 防呆為結構參數，非可調配額）。詳見 `b §3`。
- **風險端點表 71 條**：受測者落在端點 (trait_id, band) → 相關交互強制納入「作答校準與風險提示」子區塊。含 property_peak 特質 **CIA_27／SPA_09 的 A、C 兩端皆評**。人閱視圖見 `風險端點表_定案`。
- **構念家族補全**（⚠ **資料生成期機制，非打包層步驟**）：題目匡列某構念時，跨已測測驗補齊該家族。此補全**已在題庫表生成時做完**（22 題 scoped_traits 實測缺口 0），打包程式**不得**在 runtime 再做一次 S 擴張（會違反 00 的職責邊界；且家族表含 SDR 校準族，再擴張會把校準特質誤升全塊區，違反 b §2 註）。`construct_families_v1.json` 交付給外包**僅供稽核比對**，程式不需載入。
- **回答長度裁定**：題庫題**不限字數**（長度由輸出架構管）；自由提問**一千字以內**。落在 `b §8` 完整性檢查。
- **出口掃描 9 類硬樣式**：trait_id／band_code／聯動／分數洩漏／中文分區／HR 決策語／人口統計／誠信定罪／label 判定；everyday 白名單只擋構念式用法。

## 5. 驗證方法（交付前必跑）

1. **打包器單元檢查**（`b §6`）：注入塊數＝匡列特質數；每個交互塊兩端 ID 都存在於已注入塊；無 `['`、無空括號、無殘留代號。
2. **輸出完整性檢查**（`b §8`）：段落齊全（子集寬鬆判定）＋社會期望反應 A 段佐證措辭。
3. **紅隊實測**：以標記最密的受測者資料打包，實呼叫 LLM 數十次，出口掃描器統計殘留率；**通過標準＝內部標記殘留 0**。
